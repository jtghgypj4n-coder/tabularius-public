# OAuth authorization server and MCP connector conformance audit

## Baseline and scope

The checkout already implemented authorization code flow, S256 PKCE, one-time code deletion, a framed-denied consent page, dynamic registration limits, RFC 8414 and RFC 9728 discovery, an RFC 7009 revocation endpoint, and account/AI-access checks. Those controls were retained. The requested r22-01 and r22-11 write-ups and a separately titled connector security review were not present in the workspace search; the existing implementation, `docs/remote-connector-exposure.md`, `docs/mcp-conformance.md`, `docs/threat-model.md`, and `SECURITY.md` provided the available baseline.

This audit covers Tabularius as the authorization server for its `/mcp` resource. It does not claim FileMaker or Claris behavior. No Claris behavior was inferred.

## Changes and evidence

- Authorization form POSTs require a short-lived, host-only, `HttpOnly`, `SameSite=Strict` CSRF cookie matching a hidden value. HTTPS deployments use a `__Host-` cookie with `Secure` and root path to prevent sibling-domain cookie injection. Password approval and federated consent remain explicit, and the existing `X-Frame-Options: DENY` and CSP `frame-ancestors 'none'` remain. The browser returns only a code and optional state to a registered redirect; access and refresh tokens appear only in JSON bodies.
- Refresh consumption and spent-token recording run in one SQLite immediate transaction. A refresh token used again more than ten seconds after it was spent is treated as stolen: the current family grant is deleted and its access token revoked. Used again within ten seconds, it is refused but the sign-in is kept, because that is two requests racing (a client retry, two tabs) and not theft. The spent ledger keeps the newest twenty tokens per sign-in, is swept at each grant's absolute deadline, and when it reaches 100,000 rows drops its oldest 1,000 instead of refusing refresh, so one busy sign-in cannot lock everyone out.
- Newly issued OAuth access tokens have delegated provenance. MCP validates their recorded resource and current password mark, so a changed password or missing grant invalidates access before its hour-long expiry. Older OAuth grants with no recorded audience fail closed; file API tokens issued for other purposes keep their prior validation path.
- Refreshing a password account's grant restores the 30-day sliding window from the moment of refresh (federated sign-ins keep their fixed deadline), so an app in daily use stays signed in.
- Registration refuses `jwks_uri`, `jwks`, `sector_identifier_uri` and `request_uris` (they would need fetching) and ignores display addresses (`client_uri`, `logo_uri`, `tos_uri`, `policy_uri`), which are never fetched, shown or stored, so the metadata-document style of registration used by common connectors is accepted. A client may ask for the authorization-code grant alone. Address buckets for IPv6 are the /64 of the address written in full, so `2001:db8::5` and `2001:db8::6` count together.
- The token endpoint accepts a Basic header together with the same `client_id` in the body, an empty `client_secret` from a public client, and a missing `redirect_uri` when the app registered exactly one. A `resource` written as the server address (with or without a trailing slash) or `/mcp/` is accepted and recorded as the canonical `/mcp` address.
- Registration rejects URL metadata instead of fetching it, sanitizes control and bidirectional characters in display names, bounds the in-memory address buckets, and commits count-based eviction only with the new client. OAuth JSON errors now return a standard error code without detailed account, client, or token information.
- Generated-data tests cover redirect encoding, state, CSRF, PKCE, client and redirect binding, replay (including overlapping requests), resource and scope binding, revocation, account deactivation, password change, clock rollback and expiry, hostile metadata, registration capacity, ledger capacity and trimming, the replay grace window, sliding refresh expiry, and the accepted client spellings.

A second model reviewed this change before the pull request and found ten issues; eight were fixed here (one shared ledger cap, racing refreshes ending the sign-in, lost sliding expiry for password accounts, over-strict registration, IPv6 bucket spelling, Basic header plus body `client_id`, omitted `redirect_uri`, resource spellings). Two are left open and listed in the limits below.

## Verification and limits

Still open: the CSRF cookie uses the `__Host-` prefix only when the server knows it is behind HTTPS, so a TLS-terminating proxy without a configured public address gets the plain cookie name; the authorize form carries its CSRF value in a single cookie, so two sign-in tabs open at once invalidate each other. Registration limits are counted per process, so a cluster multiplies them.

`node --test --test-concurrency=2 --test-reporter=spec packages/server/test/oauth-conformance.test.ts`: **11 passed, 0 failed** (the registration and token-spelling cases moved to `oauth-registration.test.ts`: 4 passed). The file completed in under 30 seconds. The final combined OAuth and MCP-origin run passed **23/23**; the earlier generated-data MCP-origin and MCP-signin-parity run passed **21/21**. `npm run typecheck` and `./node_modules/.bin/tsc -p tsconfig.json --noEmit`: passed.

The older OAuth suites use a fixture that is present in this checkout, so they cannot be part of the requested synthetic-only verification. A broader nearby run was stopped when that became apparent. Two older expectations observed before the stop were updated: direct authorize POSTs now supply CSRF, and refresh replay now revokes the descendant. They were not rerun under the fixture restriction. No external OAuth provider or remote connector was contacted. TLS for public authorization endpoints remains a deployment requirement; the local generated-data tests run over loopback HTTP.
