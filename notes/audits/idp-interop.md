# Identity-provider interoperability audit

Tabularius uses the public OIDC and SCIM shapes listed in [`idp-interop-cases.json`](../../packages/server/test/idp-interop-cases.json). The test data is generated; no vendor tenant or live account was used. “Unverified” means the cited public material does not establish that exact outbound request, token claim, or retry behavior.

## Shared protocol shapes

- OIDC discovery uses `issuer`, `authorization_endpoint`, `token_endpoint`, and `jwks_uri`. A JWKS has a `keys` array; an RSA signing key carries `kty`, `n`, `e`, and commonly `kid`, `use`, and `alg`. The standard also defines EC key parameters and `x5c`; provider-specific active key types and rotation timing are **unverified** here. The fake server emits a generated RSA key. Sources: [OIDC Discovery](https://openid.net/specs/openid-connect-discovery-1_0.html), [RFC 7517](https://www.rfc-editor.org/rfc/rfc7517.html), [RFC 7518](https://www.rfc-editor.org/rfc/rfc7518.html).
- The SCIM server expects `application/scim+json`, Users and Groups resources, `PatchOp` operations, `attribute eq "value"` filters, one-based `startIndex` and `count`, and SCIM error bodies with `status`, `detail`, and applicable `scimType`. These are protocol expectations, not proof that every provider sends every form. Source: [RFC 7644](https://www.rfc-editor.org/rfc/rfc7644.html).

## Result

The generated, loopback-only in-process test covers each matrix ID-token shape, a group-overage refusal (only for the claim the provider is configured to read), invalid signature/issuer/audience/nonce/expiry and invalid group data, SCIM lookup/create, Okta-style pathless User PATCH, Authentik-style User and Group PUT, Group PATCH, active as a string, pagination and SCIM errors. It checks privilege mapping, ends an open session on deactivation or inactive-account takeover, and proves both an owned API token and a person-bound token through a shared mapping remain revoked after reactivation. No behavior marked **unverified** is claimed as a vendor conformance result.

## Second-model review

A different model reviewed the change read-only and probed it. Findings and what was done:

| Finding | Result |
| --- | --- |
| Overage was refused whenever `_claim_names.groups` or `hasgroups` was present, even for a provider reading `roles` or `wids` | Fixed: only the configured group claim counts (`hasgroups` only when that claim is `groups`); tests for Okta, PingOne and Entra |
| A string `hasgroups` passed the refusal | Fixed: `"true"` is treated like `true` |
| `groups: null` was refused although an absent claim was accepted | Fixed: null is treated as absent. A non-string entry such as `[123]` is still refused (it used to be turned into text); **recorded in `launch-decisions.md`** |
| An attribute-only SCIM update of an inactive full-access account revoked its tokens | Fixed: provisioning leaves a full-access account's tokens alone, test fails without the change |
| Savepoints outside a transaction start a deferred transaction, so the first write can fail at once with "database is locked" | Fixed with one helper that takes the write lock first and commits; the membership update, which opened a lock and never committed it, now commits. Reproduced by the reviewer with plain SQLite in WAL mode, not through the product |
| User creation was not atomic with deactivation and token revocation | Fixed: creation runs in the same helper |
| Audit said both tokens stay revoked after reactivation but the test checked one | Test now checks both |
| Pagination is tested with one request against an empty list; `hasgroups` was untested; the `expect` field in the cases file is not asserted | Pagination and `expect` remain **not covered**; `hasgroups` is covered now |
