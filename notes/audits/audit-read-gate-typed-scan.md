# r28-01 addendum: the type-checked scan and the cross-file sweep (security-adjacent)

This adds to [the read-gate inventory](audit-read-gate-inventory.md): that one lists every reader by function and gates `sortIds`, `groupSummaries`, `foundSetRows`, `portalCounts`, live presence, digests and RAG. This one adds a second, type-checked scan, a sweep that calls every route and MCP tool as a restricted account against two hosted files, and the fixes those found. Finding numbers below are this file's own.

The different-model review recorded at the end covered this code before it was stacked on the inventory; stacking changed file names (`read-gate-typed*`) and the hashes of the inventory's allow-list entries for the call sites these fixes edit, and nothing else.

Invariant: no code path returns field values, record counts, found-set sizes, sort orders or aggregates to a caller without passing the privilege and record-level-access gate, and a new reader that does not fails CI until someone classifies it.

Method, two halves.
- **Static inventory.** `scripts/read-gate-lib.ts` loads every `packages/*/src` file with the TypeScript checker, resolves each call to a `Store` read method (`READ_APIS`) and each SQL call on a record table or a data-bearing internal table, and marks a call *gated* when an argument (or a property of an options object) has the type `Privileges`. 549 readers were found, 145 pass the caller's privileges. The rest are classified in `scripts/read-gate-typed-allowlist.json` (307 entries, each `{file, within, api, count, gate, why}`; `count` is exact, so a new call in the same function fails; an entry with no read left fails). Readers include SQL run on the store's connection (by any receiver named `sql`, through the store's and the calculation engine's cached-statement helpers, and with a statement held in a variable, which counts as reading data). `npm run check:read-gate` lists the unclassified sites; `--all` lists every reader. Four subagents (read-only, one per area) classified the sites; each classification was checked against the code, and 21 of them came back SUSPECT and were looked at one by one (below).
- **Dynamic sweep.** `packages/server/test/read-gate-sweep.test.ts` seeds a solution with values and counts that appear nowhere else (`SENTINEL-*` values, 1,371 hidden records, 2,113 in a hidden table, a hidden container, a calculation over a hidden field, a script that returns a hidden field), and a second hosted file the restricted account has no access to (reached by a relationship and by calculations), then calls every route in `docs/reference/rest.md` and every MCP tool the server lists (hidden and visible targets; arguments fitted to each tool's declared types and bounds) as a restricted account, and fails if a sentinel value or a count only a wider view could give is in any response. A control run as a full-access account must show the values on several routes and tools, and must get a success from every route family and run every MCP tool, except those listed with a reason in the test (writers, design tools, public pages, signed links); a family or tool added later that the control cannot reach fails until someone looks.

Tests: `read-gate-typed.test.ts` (2), `read-gate-sweep.test.ts` (3), `read-gate-gaps.test.ts` (7), plus one each in `passkey-signin.test.ts`, `cleanup.test.ts`, `time-travel.test.ts` and `agent.test.ts`. Every regression test was run against the code without its fix and fails there.

## Deliberate or accepted (recorded, with the reason)
- **Redaction denylist (`storedSecretValues`).** To hide secrets from AI-visible output the server reads every secret-named field of every record and hides any AI-visible value equal to one. Nothing read is returned, but a value that is hidden tells a caller who guessed it that it equals some stored secret. Accepted: the caller can already see the field's own values only if allowed, and the guess has to be exact. *Recommended:* keep.
- **A script run with "Run script with full access" leaves its found set elevated** for the sub-script's lifetime, as FileMaker's does; the account's own found set is restored after. The run's *report* is limited (#10).
- **Cached `allowedIds` for rules that read other files** can lag one write behind the other file; the cache is dropped on any write to the file that holds the rule, not on writes to files it reads. Unverified how FileMaker orders this. Low.
- **The cross-file calculation cache (`sumKey`)** is keyed by the privileges' fingerprint; its behaviour when the *other* file's privileges change mid-pass is unverified.
- **Cleanup apply's cascade refusal** ("deleting it would delete their records") says that a child exists for a key the account can already read. One bit, only for a key it may read.
- **`trusted-process` readers** (46: sync apply and sync, backup verification, the warm worker, word index, PII scan, and store maintenance) run as the server, not as an account; each entry says which process and what it does with what it reads.

- **A found set a client supplies to a script** is its own list of ids; reading a record in it that the account may not view answers error 200 (pinned by `calc-read-privileges` and `step-write-privileges`), so the ids are not filtered up front.

## Not found
No sentinel value, hidden count or hidden table name reached a restricted account on any documented route or MCP tool after the fixes (the sweep covers the REST routes of `rest.md` including OData, SQL, XML, web client, live, design, debug, assistant, agent, digests and cleanup, and all MCP tools). pgwire is covered by its own suites (`pgwire-catalog*`, r28-09), not by this sweep.

## Different-model review (not the author)
Run over the first version of this change. It confirmed by running them two leaks the author's classification had called minor or design-gated (#12, #13 above), found the agent-step fix incomplete (#14), and found the sweep and the scanner too blind to give the guarantee claimed:
- The sweep sent Basic credentials to routes that require Bearer, covered one file, left 23 of 92 MCP tools failing validation before they ran, and its control needed only 6 leaks in total. Now: Bearer on every route that wants it, a second hosted file, arguments fitted to each tool's schema, and a control that must get a success from every route family and run every tool (exceptions listed with a reason in the test).
- The scanner dropped `sql.prepare` with a statement in a variable, did not follow the store's and the calculation engine's statement caches (the reads in `related.ts` and `calc.ts` were invisible) and recognised only a receiver named `.sql`. Now those are readers and are classified (45 new entries). Not covered, as a known limit: connections other than the store's own (`readOnlySql` for MCP `sql_query`, the in-memory OData `$apply` database, the RAG index and the result cache), which the review checked by hand and found fed only through the gated Store reads, and calculation passes made without privileges (`newPass()`), which the scan does not look for. Two of those that were reachable are fixed (#13, #15).
- Stale allow-list text was corrected (the evaluate entries, `valueOf`, `describeRecord`, `warm-worker`).
- Not changed, for the record: `Get ( RecordNumber )` was made O(log n) per record (`viewableCount`); automation conditions are worked out with the run-as account's privileges, so a condition on a field that account cannot see no longer fires (release note in launch-decisions.md); `get_container` with full read access reads any container by id including those of deleted records (unverified, not changed).

## Second different-model review (of this change stacked on the inventory)
A different model than the author reviewed the stacked change and ran code. Confirmed and fixed here, each with a test that fails without the fix:
- **High.** `explain_value` on a *stored* calculation that reads through a relationship worked its references and steps out again with no privileges, so the values of records and files the account may not view showed in them (the stored value itself is stored data and is unchanged). Now the re-run carries the account's limits when the formula reaches another table occurrence (extended below to any route into another file). Test: `read-gate-gaps.test.ts` (`ExtStored`).
- **Medium.** Execute Data API `create` with `portalData` was refused (200) when the new record did not satisfy the account's view rule, unlike the REST route; it now passes `justCreated` too. Test: `data-api-step-options.test.ts`.
- **Low.** A layout calculation on a record being edited was judged on the unsaved edit, so it went blank when the edit would hide the record; it is now judged on the saved record. Test: `read-gate-gaps.test.ts`.

Gaps in the checks, recorded not fixed (each needs its own design): the typed scan does not list `Calculations.value`, `context`, `explainEvaluation` or `relatedRecs` as readers, so the formula engine is covered by the sweep and tests only; "gated" means an argument's type includes `Privileges`, so a `Privileges | undefined` that is undefined at run time counts; the allow-list counts per file, function and API, so swapping one call for another of the same API in the same function is not noticed; the sweep's restricted account cannot use design tools, so `explain_value` and the formula tools are swept only through `read-gate-gaps.test.ts`; the sweep's data has no visible record with hidden related records, and finds sentinel text case-sensitively and counts only at four exact numbers.

Not confirmed, kept for the owner: `portalCounts` answers 200 for a record the account cannot view while `evaluate` answers 101 (whether a record exists); FileMaker may count "No Access" records in `Get ( FoundCount )` and `Get ( TotalRecordCount )` (unverified).

## Third different-model review (of this port)
A different model than the author ran the ported change against the private base and found the following; each is fixed here with a test that fails without it.
- **Medium-high.** The explain fix was incomplete: a stored calculation that reads another hosted file through `ExecuteSQL` (any route that is not a `Table::Field` reference) was still worked out with no limits, so `explain_value` showed the other file's value in a step. Now the explanation's context carries the account's privileges for every stored calculation; for a stored calculation that may read a field the account may not (it names one, a calculation behind it does, or it reaches fields by name with `Evaluate`, `GetField` or `ExecuteSQL`, also through a custom function), the steps are worked out without that field, the stored value stands as the result, a note says so, and no verdict is given on whether the stored value is still current. A first attempt that let the record's own fields read through leaked them in `steps` and `result`; a second kept a yes/no verdict made on them, which an account that can set a global (or change a related record) could steer until a hidden number was known (found in review). A calculation that reads no such field is explained in full, the verdict included, so `record-check` still finds a stale visible calculation. Tests: `read-gate-gaps.test.ts` (ExtSql), `explain-privileges.test.ts` (hidden, masked and row-rule accounts over ten own-field and four other-record formula shapes, a calculation behind another, a visible-only calculation, and a verdict that is the same for every guess of a global), `explain.test.ts`, `record-check.test.ts`. Test: `read-gate-gaps.test.ts` (an `ExtSql` field).
- **Medium.** `Get ( RecordNumber )`, `Get ( FoundCount )` and `Get ( TotalRecordCount )` scanned the table once per record when the view rule is never cached (random, clock, `$` variable or a global field). The list of viewable ids is now kept for the page of records being read. Test: `read-gate-gaps.test.ts` (the scans of a page do not grow with its records; counted, not timed).
- **Low-medium.** A stored global read by a script of an account that may view no record returned empty with error 0; it gives error 200 again, as before (with a viewable record the global is read from it). Test: `global-field-read.test.ts`.
- **Low-medium.** `updatePortals` through a parent the account may not view: the view check is now pinned by a test, as is the container write through a portal row (both fail without the check).
- **Low.** The passkey registration answered 500 for `{"response":[]}`, `{"response":{}}`, a non-string `attestationObject`, `clientDataJSON` or `challenge`, and a challenge that was never issued or has expired (error 960); it answers 400. Test: `passkey-signin.test.ts`.
- **Tests added where a change could be reverted unseen:** Execute Data API `read` of a layout with no access (via `layout.response`), the agent step that creates and deletes a record the account may not view, and the cleanup history through the MCP tool. A typed-test assertion had an `&&`/`||` precedence slip.
- **Not testable through its route:** the web client's `explainRelated` call passes the privileges as well, but its route already refuses an account whose set in the other file cannot see formulas and read everything first (`mayRead`), so that argument is defence in depth that no request can observe.
- **Known gaps in the scan, not fixed here:** it does not see a call made through element access (`store['find']`), `bind` or `call`, a `.prepare` on a connection held in a variable of another name, or an options variable whose `privileges` property is undefined at run time (a property that is present counts as gated). Each needs its own change to `scripts/read-gate-lib.ts`.
