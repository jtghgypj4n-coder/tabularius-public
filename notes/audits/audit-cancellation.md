# Cancellation audit — r22-06

Tabularius source audit and targeted fixes. No production data or source database samples were used. This is not a certification that every operation has a bounded cancellation latency.

## Existing work retained

The first source search was against `main`. It already supplied script step polling, periodic event-loop yields, user-abort handling, cancellable timed pauses, server-script queue cancellation, transaction rollback on unwinding, run-owned temporary-file cleanup, backup shutdown cancellation, AI HTTP signals, and sync lifetime checks. Duplicate implementations of those mechanisms were dropped. The worktree also contains later changes than `main`; these were retained.

No script-text rules, error-code assignments, dependencies, workflow files, release actions, or changes to the protected directories are part of this item.

## Compatibility and limits

Halt Script and Exit Script dispatch cases were not changed. Ordinary Halt Script still follows its existing behavior; only externally canceled runs discard pending record edits. Existing Allow User Abort Off and “waiting for the person” handling are retained. Administrator cancellation continues to return error 1. No cancellation is remapped to error 8; the local error table does not define 8. Vendor-specific or historical error-8 behavior is **unverified**. Full Claris parity, callback timing after client disconnection, and remote-service cancellation semantics are **unverified**; no new claims about these were inferred.

No `AbortSignal.any` is used in the new links. Parent listeners are linked by hand, detached after completion or abort, and deadline timers are cleared. Repeated linking is covered by 2,000 disposable links under a fake clock. Work remains cooperative where the existing API is synchronous. Native SQLite interruption and background-job cancellation endpoints are remaining gaps, not solved by this patch.

## Regression evidence

New regressions live in `packages/scripts/test/cancellation.test.ts` and `packages/server/test/cancellation.test.ts`. They use generated databases, fake blocking hooks, a fake deadline clock, local SMTP/HTTP servers bound to `127.0.0.1`, and generated worker code. They cover transaction rollback, record lock release by a subsequent writer, temporary file removal, preservation of previous exports, listener cleanup, worker exit, SMTP disconnect, retry suppression, restore cleanup, backup queue recovery, sync logout, agent copy cleanup, and independent server-session continuation.

Every test subprocess inherits a PATH containing stubs for `launchctl`, `systemctl`, `sc`, `git`, `npm`, `curl`, and `sudo`. Stubs write a marker and exit 99; test teardown fails if the marker exists. An initial compatibility run was rejected by this guard because the existing admin-console test asks `serverCommit()` to run git. That unrelated admin metadata test was dropped from final verification; the existing server-queue cancellation and user-abort compatibility cases are retained. No real prohibited command ran.

Final verification uses `--test-concurrency=2`, a 45-second per-file timeout, and no real-time timing assertions in the new regressions. Targeted TypeScript checking covers the changed server/script modules through the new tests and the upload/sync entry points. The guarded suite passed 19 tests in 4.054 seconds overall, so every selected file completed within that time and well below 60 seconds. The admin metadata case was excluded with `--test-skip-pattern="admin console:"`. Targeted TypeScript checking exited 0, `git diff --check` passed, and the command marker was absent. After the final plugin-listener cleanup, all 14 new regression tests passed again in 4.777 seconds, with no prohibited-command marker. No commits or pushes were made.
