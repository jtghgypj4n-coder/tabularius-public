    Sync with FileMaker Server 
    
    
    Keeps a hosted file in step with its copy on a FileMaker Server, through the server’s Data API. A check only reads: it lists what would be sent, what would be brought in, and the records changed on both sides. Nothing is sent or changed until you ask for it below, and only if the setup allows it. Files marked capture-only never sync.
    
    
    
    
    
    
     Used once, never saved.
    
    
    
    
    
      
    Setup 
    
      
    
        
        
        
        
      
    
      
    The password is never saved by the console. A scheduled sync needs a password file or TABULARIUS_FMS_PASSWORD on the server; otherwise type it when you check.
    
      
    
        Tables to keep in step
        
    Each table needs a field holding the same UUID on both sides, and a modification timestamp field on the FileMaker side.
    
        
    
        
    
      
    
      
    
        What the console may do
        
    
        
    
        
    
        
        
    Both are off until you turn them on. Even then, each run has to ask for them.
    
      
    
      
     
    
    
    
    
    
    
    
      
    Scheduled syncs 
    
      
    A scheduled sync checks by default: it reads both sides and writes neither. A schedule can also be set to send to FileMaker, bring its changes in, or both, but only where the setup above allows it, and it never includes deletions. A record changed on both sides stops a run before anything moves and raises an alert here, on the Security health list and in the server’s Event log, until you settle it. It needs a password file or TABULARIUS_FMS_PASSWORD.

      Sync log
      
    Everything sent to FileMaker and brought in, newest last. A run that stopped half way shows its unfinished records as interrupted.
    
      
     
    
      
    
    
    
  
    
  
    
    
    Stale calculations 
    
    
    FileMaker only recomputes a stored calculation when its own record changes, so one that reads other records (ExecuteSQL) or names fields at run time (Evaluate, GetField) can fall behind. A converted file keeps FileMaker's stored values until you bring them up to date here. Checking changes nothing; a refresh is one batch you can undo, and every value it sets is in the audit log.
    
    
    
      
      
      
    
    
    
    Check a file to see its stale values. Large files take a moment: up to 10,000 records per table are looked at.
    
    
    
    
    
    
     
    
    
    
  
    
  
    
    
    Dependencies 
    
    
    How the hosted files rely on one another: a file's table occurrences, value lists and scripts that reach into another file. A reference to a file that isn't hosted shows as "not hosted" (the reference FileMaker draws in red). Use it before moving, renaming or removing a file. Reading only — names of files, tables, occurrences, scripts and value lists, never record data.
    
    
    
    
    
  
    
  
    
    
    Running on the server 
    
    
    Server-side scripts (Perform Script on Server, schedules, automations and inbound hooks) take turns. Canceling a waiting script means it never starts; a running one stops at its next step.

    Script schedules 
    
    
    Scheduled scripts run as the account you choose, within its privileges. They never reach the network or send mail, and a capture-only file is never scheduled. A schedule whose last run failed shows up under Security health.

    Slow finds

    AI use 
    
    
    
    
    
  
    
  
    
    
    New solution from a description
    
    
    Say what the file is for ("a small CRM with companies, contacts, deals and a pipeline view"). The assistant plans the tables, fields, relationships, value lists, layouts and starter scripts; the plan is checked on an empty scratch file and its scripts are tried there, offline. Nothing is created until you press Create, and then the whole plan goes in at once or not at all.
    
    
    
      
      
      
    
    
    
    
    
    
    
    
      
      
    
    
  
    
  
    
    
    AI digests 
    
    
    Dashboards worked out on a schedule and summarised by the assistant, as the account that set each one up. They are shown here and on the dashboards page in the web client, never emailed; one posted to a webhook is sent only when the server allows webhooks. Set them up from a dashboard in the web client.
    
    
    
    
    
  
    
  
    
    
    Plug-ins 
    
    
    Plug-ins run in the server's sandbox and can only do what their listing says. Add one with the plugins install command; here you turn it on for a file and set the secrets it asks for.
    
    
    
    
    
  
    
  
    
    
    Connections 
    
    
    Outside services your solutions use by name, such as S3-compatible storage, a web API or a mail account. Their keys are typed in here and kept encrypted on this server; scripts, plug-ins and AI tools can use a connection but never see its keys. A connection the AI drafts does nothing until you check it, add its keys and approve it here.

    Unusual access 
    
    
    Recent patterns worth a look: failed-sign-in bursts, lockouts, a sign-in from a new place, one account signing in from several places, a dormant account waking, and protections turned off. Drawn from the security log over a recent window — a heads-up, not an automatic block.
    
    
    
      
      
      
    
    
    
    
  
    
  
    
    
    Account usage
    
    
    What each account has done in the file you chose above: requests by where they came from (web client, Data API, AI apps), days active and sign-ins. Counts only, never what was asked. Accounts that did nothing are listed too, so unused ones stand out.
    
    
    
      
      
    
    
    
    
  
    
  
    
    
    Security health 
    
    
    A least-privilege and hygiene check of a hosted file, built from what it already knows. Nothing here is changed unless you ask: the only one-click fix is revoking a broad API token.
    
    
    
      
      
      
    
    
    
    
    
    
    
    
      
    Account access
    
      
    For an account that can't sign in at all (its FileMaker password couldn't carry over on import, or it's locked out) — no Terminal access needed.
    
      
    
        
        
        
        
      
    
      
    
        
        
      
    
      
      
    An empty password reaches anyone who can reach that network, so leave this off once every account has one. Off by default.
    
    
    
  
    
  
    
    
    Security events 
    
    
    A plain-English timeline of sign-ins, lockouts, and every change to accounts, privilege sets, passwords, second factors, API tokens, AI agents and schema. Privilege refusals are sampled and repeat-suppressed; this feed does not count every attempt. Configuration names can contain personal text. Record edits are in the Audit log; this is the security log on its own.
    
    
    
      
      
      
      
      
      
      
      
      
    
    
    
    
  
    
  
    
    
    Audit log 
    
    
    Who signed in, who was locked out, and every change to accounts, privilege sets, passwords, second factors, API tokens, schema and records.
    
    
    
      
      
      
      
      
      
      
      
      
      
    
    
    
    
    
    
    
    
      What the log keeps, and for how long
      
    Every record created, changed, deleted or duplicated is logged on its own, with the account, the time, where it came from and each field's old and new value. Container files are logged only by name, size and hash. Entries are linked by hashes, so one that is edited or removed afterwards is found by Verify. Values left out below can't be put back by Undo or a revert.
    
      
    
    
    
    
    
  
    
  
    
    
    View as a privilege set 
    
    
    See a layout exactly as a privilege set would: only the records it may view, with fields it can't see left out. Read-only, and each preview is written to the audit log.
    
    
    
      
      
      
      
    
    
    
    
    
    
  
    
  
    
    
    What a set or account can do 
    
    
    Pick a privilege set, or an account, and see everything it can open and change across the whole file — records in each table, the fields it can and can't see, which layouts and scripts it may use, and the ways in from outside the web client — each with a plain reason. Read-only, and each check is written to the audit log.
    
    
    
      
      
      or
      
      
    
    
    
    
    
    
  
    
  
    
    
    Test this account 
    
    
    Sign in as an account, on paper: every layout and script in the file, as this account's own privileges would actually meet them, including a runnable script that tries to jump to a layout or another script it can't reach. Nothing runs and nothing is written, but each run is recorded in the audit log.
    
    
    
      
      
      
    
    
    
    
    
    
  
    
  
    
    
    Access review Export CSV
    
    
    A one-click "who can do what" audit: every active account, its privilege set, and (for a non-full-access account) its own access to each table, with extended privileges, last sign-in and two-factor status alongside. Read-only.
    
    
    
      
      
      
    
    
    
    
    
    
  
    
  
    
    
    Compare two sets 
    
    
    Pick two privilege sets and see, line by line in plain English, how the second differs from the first — record access per table, field, layout, script, value list, menu commands and the ways in from outside. Read-only.
    
    
    
      
      
      
      
    
    
    
    
    
    
  
    
  
    
    
    SSO group mapping 
    
    
    When someone signs in through an identity provider (Google, Microsoft or Apple), the privilege set they get is whichever of these rows first matches their email address, their email's domain (as "@example.com"), or one of their groups, in that order. An email (or its domain) matches only when it can be trusted: the provider says it verified it (Google and Apple do), the provider is one organisation's Microsoft tenant and the person is a member there rather than a guest, or it is set up with trustEmail. Otherwise anyone who can put an address into their profile could sign in as its owner. A group with an "@" in its name never matches, for the same reason. This test assumes a trusted email.

    Test with this user
    
    
    Try an email and/or a comma-separated list of groups, exactly as an identity provider would send them, and see which row above would match and what that privilege set can do. Nothing is signed in or changed.
    
    
    
      
      
      
    
    
    
    
    
    
  
    
  
    
    
    Provisioning (SCIM) 
    
    
    Let an identity provider such as Okta or Microsoft Entra ID add, deactivate and remove this file's people, and move them between privilege sets, on its own. Each person becomes an external account named by their email, which single sign-on then matches them to. Groups are this file's privilege sets (never [Full Access]): putting someone in a group gives them that set. Accounts with a password are never touched.
    
    
    
      
    
    
    
    
    
    
      
      
      
    
    
    
    
  
    
  
    
    
    Field access 
    
    
    Pick a privilege set and a table to see, and change, which of its fields that set can modify, view only, or not see at all. This is the one part of FileMaker Pro's "Edit Privilege Set" this console couldn't change before; everywhere else the record access a set has is still edited in FileMaker Pro and re-imported. Changes take effect for every account on this set the moment they're saved.
    
    
    
      
      
      
    
    
    
    
    
    
  
    
  
    
    
    Least privilege 
    
    
    Access a privilege set grants but nobody using it has used lately: write access to a table (a candidate for trimming to view-only), ways in such as the Data API, OData, SQL or AI apps (a candidate for taking the extended privilege off), and layouts and scripts nobody on the set opened or ran. It can't tell whether an unused view grant is safe to drop, and a layout or script used only once a year looks unused, so read it as "access nobody uses lately", not a full audit. Read-only.

    Console passkeys 
    
    
    An extra way to sign in to this console, alongside the one admin password. There is no per-person login here, so a console passkey isn't tied to anyone in particular — anyone who registers one, or anyone who already has one, can sign in with it, the same as everyone already shares the one admin password.
