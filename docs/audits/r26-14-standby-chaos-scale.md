# r26-14 standby and replication chaos at scale

## Scope and baseline

The requested r24-02 artifact was not present in this checkout's docs, notes,
or tests. The existing implementation already had numbered WAL changes, a
ten-minute/256 MiB retention window, a 32 MiB response limit, two concurrent
whole-copy slots, and recopy on a changed run or a missing change. The existing
standby test already covered a primary restart, a standby restart, design
changes, and takeover. This work kept those mechanisms and exercised the gaps.

The invariants checked here are: an acknowledged sequence is a contiguous
prefix of one run; lag is current primary sequence minus that acknowledgment;
a failed or stale copy cannot become whole; and a promoted standby cannot accept
later changes from its former primary.

## Seeded profiles

`packages/server/test/standby-chaos.test.ts` runs three seeds of a 5,000-change
deterministic profile. `scripts/standby-chaos.ts` runs the same model at larger
counts. It generates integer changes and synthetic container hashes; it does
not allocate a million WAL buffers or benchmark SQLite or a network. The
fault schedule includes a divergent follower and full recopy, a primary run
change during copy, disk full, a flapping link, an older standby (modelled only), two follower
positions, promotion during catch-up, and schema transitions. Its assertions
cover prefix digests, container hashes, lag, bandwidth, and the time budget.

Measured on this run with seed 26014 and 1,000,000 generated changes:

| Bandwidth cap | Virtual catch-up | Whole-copy position | Replayed changes | Virtual replay rate | Largest 100 ms transfer |
| --- | ---: | ---: | ---: | ---: | ---: |
| 512 KiB/s | 198.5 s | 600,000 | 400,000 | 2,040 changes/s | 52,428 bytes |
| 1 MiB/s | 99.7 s | 600,000 | 400,000 | 4,077 changes/s | 104,857 bytes |

The runner itself completed each profile in about 0.02 seconds of wall time.
Those replay rates are simulated transfer rates under 256-byte changes, not
observed production replication throughput. Copying container files and
SQLite write cost are not included in the capacity model. The live loopback
tests verify protocol behavior and data integrity with small generated files.

Run the large profile with:

```sh
node --no-warnings scripts/standby-chaos.ts --changes=1000000 --seed=26014 --bandwidth=524288 --budget=900
```

It needs one CPU core, about 512 MiB available memory, and negligible disk.
The 5,000-change CI profile uses the same script through the test file and
finishes well under the per-file limit. `--changes`, `--seed`, `--bandwidth`
(bytes/s), and `--budget` (virtual seconds) are model knobs. On the live server,
`REPLICATION_EVERY` is 1 second, retained logs are bounded by ten minutes and
256 MiB, a response is capped at 32 MiB, and at most two whole copies run at
once. These live constants are not CLI bandwidth controls. `StandbyOptions.wait`
sets the long-poll interval; its default is 25 seconds.

## Fixes verified on loopback

- `tabularius_standby_behind` is computed from the latest primary sequence and
  the last sequence a standby asked to follow from. Receiving bytes alone is
  not treated as an acknowledgment. Per-process standby IDs separate two
  followers on the same address.
- A disconnected or stale whole copy releases its copy slot, cleans up its
  temporary file, and does not publish a successful response.
- The standby checks the store format before replacing its local SQLite file.
  A newer format is refused with an upgrade message. It does not check a
  replication protocol version: the protocol has one version.
- A copy is published only after the standby checks the replication position the primary sent (both the sequence and the whole-after number present, plain digits, whole-after not below the sequence) and that the store format is not newer than this server supports.
- Standby ids are chosen by the caller to tell followers on one address
  apart; they are not authenticated identities.
- Crash checkpoints cannot be armed when `NODE_ENV` is `production`. Arming is a function only test code calls; no request, setting or
  environment variable reaches it, so an unset `NODE_ENV` permits it by design.

All traffic in the integration tests binds to loopback. The tests use generated
SQLite stores and generated byte strings, with no child processes.

## Not covered: externally stored container files

Standbys copy the database file and its changes only. Container files kept
outside the database (the `RC_Data_FMS` and `Files` folders of a converted
FileMaker Server file) are not copied to a standby, as before this work, so a
standby that is promoted does not have them until they are copied by other means
(for example a file-level copy of those folders). A transfer was built and then
withdrawn from this change because it could not show that the container files
match the copied database when the primary changes them during a copy; it is kept
on the branch `claude/r26-14-standby-external-transfer` for a redesigned follow-up.

## Remaining measurement limit

A physical million-write loopback benchmark with real WAL retention, disk-full
injection, and throttled sockets was not run. The measured million-change rates
above should be used to size the model's transfer budget, not to promise a
production throughput or recovery time.
