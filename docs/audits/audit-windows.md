# Windows readiness audit

This is an offline source audit and simulated regression check, **not Windows certification**. No Windows machine or PowerShell interpreter was available. Windows execution, filesystem sharing and service-manager behavior remain **unverified**. No behavior of FileMaker was inferred from these tests. The changes preserve existing data names, including `.openhbam-*`, `~/.openhbam`, `<name>.openhbam.sqlite` and the `openhbam` scheduled task. <!-- known-difference: Windows hosting ;; Windows execution, filesystem sharing and service-manager behaviour have only been checked offline and by simulation ;; Windows hosting may behave differently from the simulated tests ;; Run the checklist below on a real Windows machine -->

## Scope and method

The audit searched `process.platform` and `win32` throughout `packages/*/src` and `scripts/*.ts`, then checked filesystem renames/removals, directory fsync, path separators, URL-to-path conversion, filename construction, child processes, signals, modes, symlinks and line endings. The platform inventory below records the branches, including those already correct. Literal `/` in HTTP routes, archive entries, object-store keys and stored portable paths is intentional; `:` in time, SQL field qualification, IPv6 and authentication is not a drive separator.

Tests build synthetic data inside temporary directories, exercise `path.win32` and `path.posix` on the same host, and inject platform values and filesystem failures. New tests do not spawn subprocesses, run services, install software, execute PowerShell or contact a network. Existing HTTP integration tests use only loopback. A guarded PATH for verification replaces `launchctl`, `systemctl`, `sc`, `schtasks`, `taskkill`, `git`, `npm`, `curl` and `sudo` with marker-writing failures. A marker fails the run. Synthetic release metadata prevents the server's optional git version lookup; it is removed afterwards. No customer or downloaded sample file was opened.

## Real Windows acceptance checklist

Use a disposable Windows 10/11 or Windows Server VM, NTFS, an ordinary user, and a separate administrator account. Record OS/Node/PowerShell versions, CPU architecture, filesystem, path length and aggregate pass/fail/record counts only. Do not publish record screenshots, exports, credentials or `.fmp12` files. Repeat the core checks on x64 and ARM64 when releasing both builds. All expected results below are **unverified until recorded on Windows**. <!-- known-difference: Windows hosting ;; Every expected result in the Windows checklist is unverified until recorded on Windows ;; Windows support cannot be claimed yet ;; Record the results on a real Windows machine -->

1. **Prepare trusted inputs.** Obtain the release and its published checksum through the release channel. Check SHA-256 (and Authenticode when provided) before extraction/execution. For source installation, use a trusted checkout with its lockfile. Place it outside the data directory, including a second run under a path with spaces, `%`, `!` and non-ASCII characters. Expected: hashes/signatures match; a changed byte fails verification and is never run. The source installer does not download app source.
2. **Install without elevation.** From the source root run `powershell -NoProfile -File scripts\install.ps1`. Follow organizational signing policy if it is blocked; do not disable it. Repeat using PowerShell 7 and run the installer twice. Expected: `tabularius help` works in a new terminal, the deprecated alias still launches, PATH has one bin entry, hosted data is unchanged, and no firewall rule or boot task is created. Simulate a bad/missing Node checksum in an isolated download test: no extraction or replacement occurs. Interrupt/fail a Node move and verify the saved Node survives.
3. **Check profile and permissions.** Confirm `.openhbam` is under the intended user profile. Inspect ACLs on that directory, hosted data, secrets, task XML and backups, removing access for unrelated users while retaining the service identity. Test access as another ordinary user. Expected: that user cannot read secrets or create a stop-request file. `chmod 600` is not evidence for this check. A SYSTEM task must be given explicit paths instead of assuming the installing user's profile.
4. **Create a generated source file.** In a local authoring application create a new unencrypted `.fmp12` with one table, two simple fields, three invented records and one generated text container; never reuse a customer/sample file. Close the authoring application. Run `tabularius export "C:\Tabularius Test\Generated.fmp12" "C:\Tabularius Test\Generated.openhbam.sqlite"`. Expected: conversion succeeds, reports one table/three records, and the generated container is readable. The repository has no general `.fmp12` writer; this step requires the local authoring tool, and conversion compatibility is unverified here. <!-- known-difference: Windows hosting ;; Conversion of a generated source file on Windows is unverified here ;; The conversion can differ on Windows ;; Convert a generated file on Windows -->
5. **Serve and open the client.** Run `tabularius serve "C:\Tabularius Test" --host 127.0.0.1 --port 18080`. Open `http://127.0.0.1:18080/app/` and `/admin/`; use only the generated database. Expected: three records, edit/save/reload succeeds, container download and thumbnails work, and Ctrl-C drains requests and releases the files. Repeat with `--workers 2` to test named pipes. Confirm a second server cannot claim the same folder using different drive-letter case.
6. **Names and text.** Try reserved device names, trailing dots/spaces, a path over the legacy limit, and case/sanitization collisions through upload/export/plug-in entry points. Import a generated UTF-8 BOM/CRLF CSV, including a quoted multiline field. Save/read CRLF script text and JSON config. Expected: invalid paths fail before publication, collisions retain all files, CSV rows and quoted line breaks remain intact, and config/script parsing succeeds. Test a long UNC share separately; shortening the destination must make the conservative limit error actionable.
7. **Personal scheduled task.** Preview with `tabularius service print "C:\Tabularius Test" --port 18080 --host 127.0.0.1`; then install with the same arguments using `service install`. Expected: one task named `openhbam`, least-privilege interactive identity, correct quoted paths, health at `http://127.0.0.1:18080/tabularius/health`. Reinstall to exercise stop/start (there is no separate CLI `service restart` command). Expected: cleanup finishes before replacement, a fresh uptime, no duplicate process, and data intact. Test a changed hosted folder too. A blocked/old server must produce an actionable refusal instead of being forcibly killed.
8. **Boot task and firewall.** In an administrator prompt use `powershell -NoProfile -File scripts\install.ps1 -Service 'C:\Tabularius Test' -System -Port 18080 -HostName 127.0.0.1`. Expected: no firewall rule for loopback. Repeat with an explicitly chosen network listener, then a changed port: one installer-owned rule with the current port. Revert to loopback: that rule is removed. Reboot/log off and verify task identity, key paths, private ACLs and restart behavior. Direct Task Scheduler End and OS shutdown are separate tests; do not assume they deliver Ctrl-C or run encryption cleanup.
9. **Upgrade and rollback.** Keep verified local copies of the current release, a newer compatible source release, and an intentionally broken *synthetic* release in separate folders. From a shell outside the installed app directory run `tabularius upgrade --from '<verified local release>'`. Dependencies must already be available in the npm cache for an offline rehearsal. Expected: pre-upgrade backup, successful health check and fresh uptime. Repeat with the broken synthetic release: old code restarts and record counts remain unchanged. Hold an app file/directory open and repeat: failure must retain the old app or `.previous`, without claiming success. Release the lock and verify recovery. First upgrade from a version without the stop listener requires a manual clean stop.
10. **Backup, restore and locked files.** With the generated server running, run `tabularius backup "C:\Tabularius Test" --to "C:\Tabularius Backups"`, then `tabularius verify-backup "C:\Tabularius Test" <printed-set> --from "C:\Tabularius Backups"`. Expected: a complete set with matching counts and no published `.partial` folder. Change one generated record, stop the server cleanly, then run `tabularius restore "C:\Tabularius Test" <printed-set> --from "C:\Tabularius Backups"`. Expected: the original count/content and container return. Repeat encrypted backup/restore with a disposable key supplied through the environment; do not print it. Hold files open during backup pruning, restore and log rotation: bounded retry or an explicit recoverable failure, never an empty/truncated replacement. After unlocking, recover any retained restore journal and verify integrity before serving.
11. **Uninstall and repeat.** Run `powershell -NoProfile -File scripts\install.ps1 -Uninstall` with the privileges appropriate to the installed task. Expected: graceful stop, task removed, data/backups retained, and the installer-owned firewall rule removed when elevated (otherwise an explicit cleanup instruction). Inspect any legacy firewall rule manually. Repeat install/uninstall and verify no unexpected task, listener, stale `.previous` directory or credential ACL broadening.

A Windows CI job running these native lifecycle checks requires owner-managed workflow work if it is not already configured. No workflow file was changed in this audit. Security-adjacent path, installer and shutdown changes require the supervisor's separate model/person review before merge.

## Verification record

The implementation includes Windows-specific tests in the store, calc, scripts, plug-ins, CLI and server packages, plus a static PowerShell test. No new test skips by host platform. `npm run typecheck` is the type gate; test commands use `node --no-warnings --test --test-concurrency=2` with explicit test files. Retained integration coverage includes path mounts, backup destinations/external containers, logs, plug-in packages and exports. Native service, upgrade, installer-download, PowerShell and release-build suites were not executed under the no-command/no-network restriction. `npm run precheck` was not run because it invokes git; no `precheck: PASS` is claimed.

Offline verification completed: **118 passed, 0 failed, 0 skipped** in the combined regression run (under five seconds total), followed by **6 passed, 0 failed, 0 skipped** in the standalone installer static run after sharing the existing checksum assertions with it. Both TypeScript configurations passed. `npm run docs:reference` reported all three outputs current; `npm run docs:plugins` completed. The original shell-download checksum cases were not run: their PowerShell assertion block is now shared with the standalone static suite, so those exact assertions were exercised without launching the shell-download cases.
