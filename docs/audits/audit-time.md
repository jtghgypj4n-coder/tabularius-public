# Time, time zones and DST audit

Scope: calculation values and `Get`, SQL date helpers, local-time schedules, backup and progressive-log names, calendar conversion, and web timestamp display. Cases use synthetic dates and records only. The existing [date/time function audit](r25-22-date-time-functions.md) covers the function families and ordinary arithmetic. The [clock audit](../clock-audit.md) covers session, token, lockout and other expiry clocks; those decisions were not repeated here.

## Results and fixes

| Area | Observed behavior and result | Compatibility status |
| --- | --- | --- |
| Calculation | Dates count calendar days; timestamp and time arithmetic counts local calendar seconds. Adding 24 hours to a spring or fall timestamp advances the displayed date by one with the same clock reading. A skipped `02:30` is representable, and the two fall `01:30` readings have the same stored value because there is no offset. `Get ( CurrentTimeUTCMilliseconds )` uses the injected instant and is independent of `TZ`; `Get ( CurrentTimestamp )` follows the host zone. | **Unverified** for the compatible product's skipped/repeated-hour arithmetic and timestamp construction. No conversion to elapsed UTC time was guessed. `get-names.ts` lists no time-zone `Get` parameter; no name or answer was invented. <!-- known-difference: Date and time functions ;; Whether FileMaker's arithmetic and timestamp construction across a skipped or repeated hour match Tabularius's local calendar-second counting is not verified ;; Adding 24 hours across a daylight-saving change keeps the same clock reading, and no elapsed-UTC conversion is made ;; A FileMaker run of timestamp arithmetic across a spring and a fall change --> |
| SQL | `NOW`, `CURTIMESTAMP` and rewritten `CURRENT_TIMESTAMP` return a local reading. The SQL clock can now be injected with `sqlDateFunctions(now)`. `fm_date_add` treats a zone-less timestamp as calendar components, so an interval may land in a skipped hour. The audit found and fixed `Date.UTC` interpreting years 0000–0099 as 1900–1999 in interval, weekday and date-difference operations. Year 0004 leap-day regression reproduced before the fix. | **Unverified** for the compatible product's DST-gap interval result and early-year SQL behavior. The fix preserves the literal year in Tabularius; it does not claim compatible-product parity. <!-- known-difference: Date and time functions ;; Whether FileMaker's SQL date intervals land in a skipped hour, and how it treats years 0000-0099, matches Tabularius is not verified ;; An interval can land in a skipped hour, and early years keep their literal value ;; A FileMaker run of SQL date arithmetic across a daylight-saving gap and in year 0004 --> |
| Schedules | A daily local-time run in a spring gap executes at the normalized later time; a repeated fall hour has two possible instants. A durable local-day claim lets only one run execute, including after restart. The claim list is bounded to 14 days and history to 50 runs. Existing tests cover editing a schedule's time, a backward clock change, and restart. Explicit cases now cover New York, London, Sydney, leap day, month end and year end. A reproduced rollback bug made a later run's history timestamp older than an earlier one. Runs now take an injectable wall clock, keep stamps in creation order across restart, and measure duration with `performance.now()`. | **Unverified** whether the compatible product fires at the normalized spring time or the first fall occurrence. Those are Tabularius scheduling choices. A clamped history stamp can be later than the host's corrected clock; it is an ordering label, not proof of the physical instant. <!-- known-difference: Date and time functions ;; Whether FileMaker Server runs a daily local-time schedule at the normalised spring time or the first fall occurrence is not verified ;; A schedule in a spring gap runs at the later time, and a repeated fall hour runs once ;; A FileMaker Server run of a daily schedule across both changes --> |
| Backups and progressive logs | Backup folder names already compare with the latest name and advance past it after a rollback or zone change. This was tested across a year boundary. Progressive log names also compare with the latest within their folder, but previously expressed an ambiguous local time. New log names start from UTC and carry a `Z` marker; readers still accept existing local-name logs. If that UTC reading is earlier than the latest label, the new label advances beyond it for sort order and is **synthetic**, while the log record keeps the factual epoch time. A repeated hour and zone change preserve filename order. | Backup and log filename formats are Tabularius data-at-rest details, so compatible-product behavior is not applicable. Old local-name log files remain ambiguous as standalone timestamps. An advanced `Z` filename is an ordering label, not a factual UTC timestamp. |
| Audit and server event logs | Stored audit rows already use UTC ISO timestamps ending in `Z`, and sequence numbers preserve insertion order when two events have the same time. A generated zone-change case confirms their stamps do not move backward. Server event log lines already carry a numeric UTC offset (`server-logs.ts`); its parser has a round-trip test. Neither format needed a change. | Log format and ordering are Tabularius implementation details. A real wall-clock rollback can still make an audit row's factual UTC time earlier than a previous row; use its sequence as the ordering key. |
| Calendar | `zonedToUtc` already moves a skipped local reading forward by the gap and chooses the first occurrence of a repeated reading. `utcToZoned`, year boundaries, leap-day validation and the iCalendar UTC `DTSTAMP` already have synthetic tests. | **Unverified** whether the compatible product resolves ambiguous imported or exported calendar readings the same way. The existing calendar code documents these as Tabularius choices. <!-- known-difference: Date and time functions ;; Whether FileMaker resolves ambiguous imported or exported calendar readings the way Tabularius does (skipped reading moved forward, first of a repeated reading) is not verified ;; A calendar entry in a skipped or repeated hour may land at a different instant ;; A FileMaker calendar run with readings in a skipped and a repeated hour --> |
| Web | `formatValue` formats the server's date/time field text as calendar components; it never parses a record timestamp as a browser-zone instant. A file's configured date element order therefore renders the same skipped or repeated reading in three tested browser zones. Calendar feed creation and last-opened metadata are instants, distinct from record field values. Their dialog display now includes a zone abbreviation so both occurrences of a fall hour can be distinguished. | **Unverified** whether the compatible product uses the same field formatting on a DST day. The dialog's metadata follows browser locale order; it is not a file date field. <!-- known-difference: Date and time functions ;; Whether FileMaker formats date and time fields on a daylight-saving day the way the web client does is not verified ;; A skipped or repeated reading shows as written in every browser zone ;; A FileMaker run showing a field value on a daylight-saving day --> |

## Clock-control inventory

These are the clock reads and `Date` constructions that matter to this audit. `new Date(value)` and `Date.UTC` used to decode a supplied date are deterministic conversions, not reads of the current clock.

| Location | Clock role and control |
| --- | --- |
| `packages/calc/src/get.ts` | `now(env)` uses `ctx.now`, then `new Date()` by default. It drives the current date, time, timestamp and UTC millisecond/microsecond `Get` answers. The audit tests `ctx.now` through DST in several zones. |
| `packages/calc/src/evaluate.ts` | Arithmetic works on numeric day/second values and does not read the clock. |
| `packages/store/src/sql-dates.ts` | `CURDATE`, `CURTIME`, `NOW`, `CURTIMESTAMP` and `TODAY` use the `sqlDateFunctions(now)` clock, defaulting to `new Date()`. `utcDate` creates a deterministic calendar value and preserves years below 100. |
| `packages/store/src/calendar.ts` | Conversion and recurrence constructors only read supplied dates. `buildCalendar` receives its UTC stamp as `opts.stamp`; callers choose that clock. |
| `packages/server/src/schedules.ts` | The constructor's `now` callback controls arming, waiting, run start and rearming. `new Date(from)` and `new Date(at)` decode those instants in the host zone. `performance.now()` controls elapsed run duration and the destination-cache TTL. No direct `Date.now()` remains in schedule decisions. |
| `packages/server/src/backup.ts` | `backupFolder(..., { now })` controls a set's initial folder label. Progressive logs receive their `at` epoch from the log shipper and name new files in UTC. `sweepCrashLeftovers(..., now)` takes an injected cutoff. Remaining direct `Date.now()` calls record completion/status, drive the separate backup scheduler, or compare filesystem modification time. `parseTime` with only `HH:MM` uses `new Date()` for the user's current local day; explicit dates and restore labels decode supplied values. |
| `packages/store/src/store.ts` and `packages/server/src/server-logs.ts` | Audit rows use `new Date().toISOString()` and sequence numbers; server log lines use `logTime(new Date())`, which includes an offset. Tests control the audit clock through Node's test timer and pass a `Date` directly to `logTime`. These are factual reporting times, not expiry clocks. |
| `packages/web/src/format.ts` | `new Date(Date.UTC(2000, ...))` only obtains the weekday of supplied field text; no current clock or browser-zone conversion. |
| `packages/web/src/calendar-dialog.ts` | `new Date(iso)` decodes a supplied server metadata instant. It does not read the current clock; the display adds the browser zone abbreviation. |

The broader expiry and duration inventory remains in `docs/clock-audit.md`. This audit makes no change to those paths.

## Verification limits

The test cases changed `TZ` within one process and supplied clock callbacks; they did not spawn child processes or read any `.fmp12` file. This verifies the Node runtime on this machine and the named IANA zones. No compatible-product runtime or documentation was available offline, so each edge comparison above remains **unverified**. The local environment refused localhost binds in the unrelated metrics case in `backup-disk.test.ts` and the server-backed `server-logs.test.ts` file.
