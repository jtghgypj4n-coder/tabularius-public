# Token file-scope request audit

File API tokens keep their account's per-file privileges, narrowed by an immutable read-only/layout ceiling. HTTP handlers use `sessionPrivileges(store, session)`; surfaces with their own extended-privilege authentication use the same `narrowPrivileges` helper. Full access is tested after narrowing. Copies rebuild the scope against the copied store rather than reusing a ceiling bound to the live store.

The audit searched all server TypeScript sources for `authorize`, `apiToken`, `privileges`, `full`, `canDesign`, and bearer/header authentication, then followed callers and copy/preview paths.

| Place checked | Authorization and privileges now used |
| --- | --- |
| `debug.ts`: scripts, current record, evaluation, runs, recordings | `sessionPrivileges(...).full` gates every request. Live runs retain those privileges; scratch runs and recordings rebuild them on the copy. Scoped tokens are refused with 403. |
| `agent.ts`: approved steps and undo | `sessionPrivileges` is passed to plan validation, execution, and undo. |
| `agent.ts`: dry-run and change previews | The handler passes the token scope; `dryRunPlan` calls `narrowPrivileges` on the copy's account privileges. Execution, elevation/Re-Login, and preview field filtering retain that ceiling. |
| `design.ts`: design, audit, reports, previews, script tests, uploads/images, and copy operations | The request gate uses narrowed `.full`. Referenced files use `.in(other).full`. The speed helper's extended-privilege check also uses `sessionPrivileges`. The exported account-only `canDesign` helper is no longer used by request handlers. |
| `security.ts`: accounts, privilege sets, tokens, migrations, second factors, and approvals | The shared gate uses `sessionPrivileges(...).full`. |
| `automations.ts`: list, changes, and dry-run | The shared gate uses `sessionPrivileges(...).full`, so scoped tokens cannot install or run account-level automations. |
| `live.ts`: design presence | Uses the request's narrowed `.full`. |
| `live.ts`: event streams | Recomputes `sessionPrivileges` per event. Design events require narrowed `.full`; record/table events use the same privileges with destination-file resolution. |
| `live.ts`: records, locks, and viewers | Uses narrowed privileges for record visibility/editability and table filtering. |
| `changes.ts`: polling and long-poll feeds | Uses `sessionPrivileges` and filters entries by table/record access. |
| `sql.ts`: shared SQL/OData authentication | API tokens use `narrowPrivileges`; ordinary session tokens use `sessionPrivileges`; Basic credentials remain account authentication. Surface/extended-privilege checks remain. Layout-scoped tokens are rejected under both Bearer and `X-FM-Data-Access-Token`. |
| `sql.ts`: queries and table metadata | Uses the shared narrowed privileges, `.readsEverything`, and `.in(target)` for external tables. Queries are SELECT-only. |
| `odata.ts`: models, metadata, records, containers, writes, and scripts | Uses the shared narrowed privileges from `sql.ts`; read-only writes/scripts are refused, and layout-scoped tokens never enter this table-oriented surface. |
| `dataapi.ts`: records, metadata, globals, portals, containers, and every script phase | Uses `sessionPrivileges`; explicit layout and read-only gates remain. The script engine retains the token ceiling and destination privileges. |
| `dataapi.ts`: password changes, passkeys, and recovery-code management | Rechecks `sessionPrivileges` and refuses scoped API tokens for account-credential management. Password/MFA checks during initial login remain account authentication, not token authorization. |
| `webclient.ts`: data, formulas, buttons, triggers, commands, imports, and exports | Uses `sessionPrivileges` and passes it to the store, calculators, and script engine. |
| `webclient.ts`: paused-run/file answers and preferences | File answers recheck `sessionPrivileges` and run ownership; execution retains the run's narrowed privileges. Preferences already refuse scoped tokens and recheck session privileges. |
| `assistant.ts`: availability, data, design, and internal MCP tools | Uses `sessionPrivileges` for full/design/whole-file decisions. Both ordinary and streamed requests pass token scope through `chat`/`answer` into the internal MCP identity. `chat` snapshots the scope before model calls; tool calls enforce that ceiling independently of the offered-tool filter. Scoped personal-data stand-ins use the same identity as internal MCP. See the [assistant regression tests](../packages/server/test/token-file-scope.test.ts) listed below. |
| `dashboards.ts`, MCP `save_dashboard`: reads, previews, and persistence | Reads and previews compute data under narrowed privileges. Every scoped token, including read-only tokens and writable layout-scoped tokens, is refused for persistent creation/update/delete/replacement; ownership cannot override the ceiling. `canChange` is false for scoped tokens. HTTP and MCP enforce the same policy, protecting dashboards consumed by unrestricted scheduled digests. See the [dashboard regression tests](../packages/server/test/token-file-scope.test.ts) listed below. |
| `digests.ts`: creation, execution, modification, deletion, listings, details, and run history | All scoped tokens are refused before digest operations or saved results are read. Ownership does not authorize a scoped token; `mayRead` also enforces this. Unscoped authorized accounts retain access to their digests and saved results. Scheduled execution still uses the saved account, but scoped tokens cannot create/modify its digest or change its source dashboard. See the [digest and schedule regression tests](../packages/server/test/token-file-scope.test.ts) listed below. |
| `cleanup.ts`: HTTP handler and scans | The handler uses `sessionPrivileges`. Scan helpers retain `.in(owner)` even when the originating account has full access; undo checks also retain narrowed privileges. |
| `import-mapping.ts`: fields, duplicate keys, writes, and undo | Retains incoming narrowed privileges. Duplicate-key lookups resolve `.in(owner)` before applying record visibility, rather than dropping privileges because the caller's file grants full access. |
| `summarize.ts`: stored and calculated/related summaries | Retains incoming privileges and resolves each owning file's field/record permissions before querying or evaluating. |
| `insight.ts`, `record-search.ts`, `record-context.ts`: profiles/search/context | Profiles and search retain incoming privileges, including external-file restrictions. Record context resolves the owning file before treating local full access as unrestricted. |
| `mcp.ts`, `mcp-design.ts`: file tools and design gates | `privilegesIn` checks file binding and extended privileges, then calls `narrowPrivileges`. Tools use that object for data and full-access checks. |
| `script-failure.ts`: MCP explanation scratch copies | MCP passes retained privileges and token scope; the copy rebuilds narrowed privileges before running the script. The existing design-access gate also refuses scoped-token access to this tool. |
| `index.ts`, `host.ts`, `containers.ts`: container/image downloads | Downloads require a file/id-bound signed URL; an arbitrary file API token does not authorize a download. Data API/web reads issue those URLs after narrowed field/record checks. |
| `admin.ts`, `adminapi.ts`, `uploads.ts`: server console and solution uploads | Separate server-admin authentication: console password/cookie or configured loopback access, write header, and independently minted Admin API tokens. File API tokens do not satisfy these credentials. |
| `replication.ts`, `inbound-hooks.ts`: replication and inbound hooks | Separate replication/hook secrets. They do not authenticate file API tokens; hook execution uses its saved account. |
| `schedules.ts`, automation/digest execution | Saved account privileges in each file. Creating schedules requires server-admin authentication; scoped tokens cannot create account-level automations or digests through their file handlers, or persist changes to dashboards used by digests. |
| `oauth.ts`, `pgwire.ts`: login and database-wire authentication | Account/password, directory/second-factor, or OAuth grant authentication; file API tokens do not replace those credentials. Issued MCP file identities still pass through token narrowing. |
| `privilege-review.ts`, `access-review.ts`, `who-can.ts`, and server-admin account summaries | Account-policy inspection, not authentication of an incoming file token. File-token access is gated by narrowed full/design privileges or separate server-admin credentials. |

Regression coverage in `packages/server/test/token-file-scope.test.ts` includes excluded debugger reads, read-only live debugger writes, ordinary and elevated dry-run copy edits, preview disclosure, scoped full-access surfaces, SQL/OData header and surface gates, account credentials, live/design events and change feeds, external-file helper reads/duplicate detection, and script-failure copies. Unscoped/full-access positive controls remain active. Earlier assertions are unchanged.

The assistant and digest rows previously overstated protection: narrowed outer gates did not constrain an unscoped internal MCP connection, matching-account ownership, or later execution with saved account privileges. Their coverage now includes these named tests in [token-file-scope.test.ts](../packages/server/test/token-file-scope.test.ts):

- `assistant internal MCP retains the token ceiling, streamed false/true`: a deterministic local stub calls `get_record` on an excluded layout; denied tool results contain no excluded values, and neither model requests nor the HTTP response disclose them.
- `assistant snapshots its token ceiling before model calls`: mutating the caller's scope during a model call cannot widen the internal MCP identity.
- `assistant internal MCP still permits an unscoped full-access read`: the authorized positive control reads the same excluded sentinel.
- `scoped dashboard mutations are refused while authorized reads and previews remain available`: creation, persisted rename/widget replacement, and deletion are denied without changing saved state; reads/previews and unscoped writes remain functional.
- `MCP dashboard saves and replacements cannot bypass the token ceiling`: previews remain available, but scoped saves/replacements cannot modify persistent dashboards.
- `scoped tokens cannot create, run, change, delete or retrieve account-level digests and saved results`: checks collection, detail, and run-history access against a real saved result, as well as all mutations; includes unscoped controls.
- `scoped dashboard edits cannot change the source of an unrestricted scheduled digest`: an attempted widget replacement is denied and the legitimate scheduled run still reads its original allowed layout.
