# N3: UUIDv7 record identity in native files

**Status:** design note for N3 implementation. N3 changes native files only. A native record has a durable, globally portable `id` and a file-local, numeric `recordId`:

```sql
_fm_record_id INTEGER PRIMARY KEY,  -- hidden alias / SQLite rowid
_fm_uuid      TEXT NOT NULL UNIQUE, -- canonical lowercase UUIDv7; public `id`
_fm_mod_id    INTEGER NOT NULL DEFAULT 0
```

The UUID belongs to the record and travels with it through a native-to-native sync or merge. The integer belongs to the table in one file. It remains the Data API locator, the join into internal side tables, and the key used by FileMaker-compatible behavior. Existing compat files retain their schema and every existing record number. `_fm_uuid` is internal metadata, not a user-defined field, so it must be protected from ordinary field edits, reserved against a user field of the same name, and omitted from `fieldData`.

## UUIDv7 generation and clock behavior

Use a small local generator, with no package dependency. `crypto.randomUUID()` is v4 and does **not** satisfy N3. Use `Date.now()` for the 48-bit Unix-millisecond prefix and `crypto.getRandomValues` (Node `webcrypto.getRandomValues`) for the remaining random bits. Set version nibble `7` and RFC variant bits `10`, then format the 16 bytes as lowercase `8-4-4-4-12` hex. Validate generated and imported IDs against canonical UUIDv7 syntax; SQLite `UNIQUE` is the final collision guard.

Within one process, hold `lastMs` and a 74-bit random/counter tail. On a later millisecond, draw a fresh tail. When `Date.now() <= lastMs`, keep the logical timestamp and increment the tail, carrying across the `rand_b` bits into `rand_a`; if the tail overflows, advance the logical millisecond and draw anew. Thus generated IDs compare monotonically **within the same millisecond** and remain strictly increasing through a clock rollback within the process. Guard the generator's state across concurrent stores in that process. Retry after a unique-constraint collision; never overwrite an existing row.

The [clock audit](../clock-audit.md) explains the clock-domain distinction: `performance.now()` is for process-local elapsed durations; public/persisted timestamps stay epoch time, and a process-local guard cannot detect rollback while stopped. UUIDv7 is an absolute sortable identifier, so its timestamp must remain Unix epoch milliseconds. Persist a per-file high-water UUID transactionally with native inserts and seed the generator from the greater of that value and the largest existing native UUID (timestamp **and tail**) on open. This also covers a latest-issued UUID whose row was later deleted. Across independent processes or files, uniqueness is probabilistic from the random bits plus the database constraint; no generator can promise global chronological order under unsynchronized clocks. A future timestamp may appear after rollback; document that as logical ordering, not the current wall time. Do not reuse the credential-expiry guard as an ID clock or alter the clock-audit behavior.

## Sync identity, conflict and alias collisions

Today `TableSyncConfig.uuidField` names a **user field** on both the local table and FileMaker Data API layout. `missingPrereqs` requires it plus a remote modification-timestamp field. `readLocalRecords` gets its UUID from that field, strips only `_fm_record_id` and `_fm_mod_id`, and reads all local rows. The planner builds UUID maps for both sides, pauses duplicate keys, keeps blank keys out, and uses `_fm_sync_map(table_key, uuid)` to remember each side's numeric record ID and modId. It flags two-sided changes by default, can apply `filemaker-wins`, `tabularius-wins` or `newer-wins`, detects changed/deleted rows with the map and `allUuids`, and pauses if local modIds go backward after a restore. `sync-apply.ts` uses those numeric IDs for actual writes, with conflict review tokens and remote optimistic modId checks. Remote deletion detection is incomplete if `allUuids` is unavailable.

For a native local side, include `fileMode` in `SyncLocal`, use `_fm_uuid` as the identity source and remove it from compared/writable `fields`; the local UUID field is no longer a schema prerequisite. For a native remote side, use the response's `id` and read-only UUID lookup (or an indexed native endpoint) to locate the current destination alias. Make UUID source an explicit adapter/config mode rather than guessing from a field's presence. Keep the existing configured user UUID field for a real FileMaker or compat endpoint. Do not require a user-visible UUID field to exist merely to sync native files. Keep `modTimestampField` only where the remote adapter needs it for incremental FileMaker reads or `newer-wins`; native-to-native sync can use native version/change tracking, but must define a reliable deletion feed or full UUID census before claiming deletion convergence.

The map remains keyed by `(table_key, uuid)`, with aliases and modIds as observations. Re-resolve the UUID at apply time and verify expected modId and UUID under the write transaction. A pull-create inserts the source UUID and allocates a **new** alias; a pull-update changes fields without changing UUID; delete targets UUID and verifies the alias before calling the existing numeric delete path. If file A's alias `12` has UUID `U`, while file B's alias `12` has UUID `V`, those are two different records. `U` is inserted in B under a free B alias and `V` in A under a free A alias. Never update, delete, adopt or report a conflict because the aliases happen to match. Conversely, the same UUID with different aliases denotes one logical record; data/version divergence follows the existing conflict policy. If the same UUID was independently assigned to unrelated content (bad import/copy), pause for owner review rather than using alias or timestamp to guess.

An old `_fm_sync_map` built with a user UUID field must not be silently reinterpreted as a native `_fm_uuid` map. Introduce a key-source/version marker or rebuild its entries only after an explicit verified mapping; otherwise pause and ask the owner to rebaseline. If two pre-N3 copies of a native file are migrated independently, their old rows receive unrelated UUIDs. Backfill one canonical copy *before* cloning where preserving identity matters, or perform a reviewed mapping; numeric alias equality is insufficient evidence.

## Migration of pre-N3 native files

On opening `fileMode === 'native'`, inspect every base table before it can serve reads or writes. For a table missing `_fm_uuid`, perform a serialized, atomic migration: add the column, assign a distinct UUIDv7 to every existing row in alias order, install its unique index and enforce non-null on all future writes. SQLite cannot `ALTER TABLE ADD COLUMN ... NOT NULL` on a populated table without a non-null default, so either rebuild the table within the transaction with `TEXT NOT NULL UNIQUE` (preserving aliases, fields, indexes, triggers/FTS and dependent metadata) or use a nullable column plus a unique index and insert/update constraints until a later safe rebuild. The target persisted invariant is `TEXT NOT NULL UNIQUE`; do not expose a partially backfilled table. Mark completion per table/version so repeated opens are idempotent. Recheck under the write lock to handle concurrent openers. A failure rolls the migration back and leaves the file unavailable rather than serving records without identities.

Backfill must not increment `_fm_mod_id`, fire user change/audit events, or change the numeric aliases, containers, text styles, relationship data, locks, found sets, or historical `_fm_audit.record_id` values. Seed a native alias high-water mark from current rows and historical record IDs when available; never give a fresh record a previously issued alias after N3. Pre-N3 history for an alias already reused may be ambiguous and cannot be repaired from the current row alone. Design-mode table creation after N3 includes the UUID column; dropping/recreating a table creates new record identities. Native `create`, `duplicate`, undo restore, audit restore, and trusted sync pull must all satisfy the invariant. Restored old snapshots migrate on first open; backups made after N3 retain the UUIDs. A normal compat open performs no UUID migration. Read-only planning (`openForPlanning`) should detect an unmigrated native file and report a prerequisite instead of writing to it.

## Test plan (for N3 implementation)

1. Generator unit tests with controlled wall/random sources: v7/variant/canonical bits, unique and lexically increasing IDs during a burst in one millisecond, rollover, backward clock, reopened-file high-water, and collision retry. Use a fixed seed to make tests deterministic.
2. Native schema and migration tests: new table and new row; pre-N3 native table with rows, multiple tables, empty table, interrupted/failing migration rollback, second open, concurrent opener, and compat file with identical aliases unchanged. Check SQLite constraints and indexes directly.
3. Store path tests: create/duplicate mint different UUIDs; get/getMany/find/portal rows return the right UUID; update leaves it stable; delete/restore and audit restore retain it; untrusted writes cannot overwrite it; deleting the highest alias followed by create does not reuse that alias in native mode. Exercise design-mode table creation and undo.
4. Data API, OData, MCP, SQL/pgwire and web contract tests: native read/find/create/portal response shapes and numeric routes; OData metadata/key/link/filter/select/expand; SQL allowlist permits only `_fm_uuid` among newly allowed internals; compat snapshots remain byte-for-byte unchanged in these surfaces.
5. Sync planner/apply tests with two native files: same UUID/different alias, same alias/different UUID, pull-create preserving UUID with destination alias allocation, two-sided edits and reviewed conflicts, duplicate UUID pause, delete conflict, stale map/alias reuse, modId rollback, sync resume and no user UUID field. Keep a separate FileMaker-adapter test for configured UUID fields and remote numeric URLs.
6. Integration checks for lock error 301, `Get ( RecordID )`, relationship/portal joins, FTS/find, text styles, audit chain verification, record-history/revert, import undo, backup/restore, and replication of a migrated file. Run targeted suites with `--test-concurrency=2`.

## Open questions for the owner

| Question | Recommended answer |
| --- | --- |
| Should native OData switch its key to UUID? | **No.** Retain `ROWID` as `Edm.Int64` key and add read-only `id: Edm.Guid`. Numeric URL and navigation compatibility is valuable; sync can use UUID lookup without changing the public key. |
| Should `id` be returned on native portal rows and create responses? | **Yes.** Every native record envelope should offer its identity. Keep existing `recordId` and `modId` beside it. |
| May clients assign/change `id`? | **No** for ordinary APIs. Permit an internal, trusted sync/import create that sets a supplied UUID once; never mutate it afterward. |
| What happens to an existing sync setup that used a user UUID field? | Keep it for compat/FileMaker. For native, require a verified rebaseline/mapping before switching the map to `_fm_uuid`; do not infer identity from aliases. |
| Must UUID order be globally chronological? | **No.** Guarantee monotonic order within one process during same/rolled-back millisecond, seed from existing native rows after restart, and rely on random uniqueness across files. Clocks on separate machines may disagree. |
| Should backfill append audit entries or bump modIds? | **No.** It is a physical identity migration. Record its schema version separately and preserve user-visible history/version semantics. |
| Should historical audit entries gain UUID now? | **No.** Keep the existing signed numeric audit chain. Expose a current UUID only when the referenced row still exists; design an explicit chain migration later if portable historical identity is required. |
| May a native numeric alias be reused after deletion? | **No for new native writes.** Persist a per-table high-water mark, seed it from rows and known historical IDs during migration, and preserve it through backup/restore. Existing compat allocation stays as it is. This prevents a new UUID from inheriting a deleted record's numeric history. |
| Is a native-to-native deletion feed in N3 scope? | **Define and test it before enabling automatic delete propagation.** Until then, perform a full UUID census or keep deletions held; do not mistake an incremental page omission for deletion. |
