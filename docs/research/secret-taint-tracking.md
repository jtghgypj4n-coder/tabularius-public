# Secret taint tracking

**Status:** design note for possible r17 work. The current AI output filters are best effort; this note describes a stronger design, not behavior already implemented.

## Threat model

An AI caller can use the web assistant or MCP tools to read records, ask for named fields, inspect related and portal data, query SQL, ask for summaries or dashboards, and run scripts. A script can read a field and then transform or encode it, put it in a local variable or `$$` global, write it elsewhere, or make it part of an action, trace, error, or exported container. A caller can repeat requests and combine results. Field names and raw value matching cannot reliably recognize these cases: `Upper`, `Middle`, `Base64Encode`, arithmetic, aggregates, aliases, and copies can all change the representation or name.

The intended security boundary remains the account's own field, record, layout, and export privileges. Taint is defense in depth for AI output: it prevents an AI tool from returning values that it could otherwise reach through a calculation or derived result. It does not grant or remove a human account's rights, repair an unsafe privilege set, prevent an authorized human from copying data, or make data safe for an AI if the account itself is meant to expose it. An explicit AI-visible exception, if added, should be a separately reviewed privilege-set policy rather than an inference from a field name.

In scope are outputs returned to the AI caller, including tool text/JSON, script results and diagnostics, SQL rows, summary/dashboard results, and file or container data delivered by a tool. This design does not cover prompt injection as a general class, covert channels through timing or result counts, model retention, outbound calls performed outside the AI-run script restrictions, or secrets that were already supplied directly in the prompt. Exact information-flow tracking cannot stop an AI from inferring a secret from a permitted predicate or count; such declassification needs a separate policy.

## Current value paths and gaps

* **Calculations.** `packages/calc/src/values.ts` represents values as tagged text, number, date/time, and container variants. `packages/calc/src/evaluate.ts` evaluates operators and functions into ordinary `Value`s. `packages/store/src/calc.ts` supplies field reads, related records, globals, `GetField`, custom functions, and `ExecuteSQL`; `Pass.values` caches calculated values. There is no provenance bit today. A secret can be transformed before the AI output boundary sees it.
* **Scripts and session state.** `packages/scripts/src/engine.ts` evaluates script calculations and keeps `$` variables on a run. Session globals implement `readVariable`/`writeVariable` and `readGlobal`/`writeGlobal` (`packages/store/src/activity.ts`); `$$` variables can therefore carry a value across script steps and, for a session, later runs. A tracking scheme that only follows a single formula result loses the taint at these writes and reads.
* **SQL.** Calculation `ExecuteSQL` is implemented in `packages/store/src/calc.ts`, including computed fields and privilege-scoped reads. MCP `sql_query` calls `Store.queryWithOrigins` and returns SQL rows through `rowsForModel` in `packages/server/src/ai-output.ts`. SQL expressions, aliases, joins, aggregates, `*`, and virtual/table-valued sources make column names insufficient provenance. SQL execution needs either value-level provenance inside the SQL engine or a conservative query/table policy.
* **Summaries and aggregates.** Whole-table and found-set summaries are computed in `calc.ts`/`store.ts`; summary results and dashboards are then shaped in `packages/server/src/summarize.ts` and `ai-output.ts`. Sum, average, min/max, count, list, group keys, chart labels, and totals can disclose information even when their output name is innocuous. A summary must combine taint from every contributing input, not only the nominal measure field. Counts and predicates need an explicit declassification decision because they can reveal facts without returning the original bytes.
* **Stored and unstored calculations.** Unstored calculations are evaluated on demand and can carry a runtime taint through their dependencies. Stored calculations and auto-enter calculations are materialized when a record changes (`Store` write paths); when recomputed, an internal calculation pass has full data. A stored result can therefore retain a secret after the source changes, be read by SQL or export without recalculation, and be copied by `Set Field` into an ordinary field. Runtime-only taint is insufficient for these persisted flows.
* **Containers and export.** A container may hold a credential file, image, or document, and a calculation can return or transform a container. Record output, script `Export Field Contents`, and file-related actions can hand bytes or a download URL to the caller. Container bytes need taint at the container value or stored-field level, and sinks must cover returned metadata, URLs, and bytes. A filename or field name check alone is not enough.

Today, `ai-output.ts` redacts secret-looking field names and some SQL origins; MCP script execution also withholds the run result when a secret-looking read or risky `ExecuteSQL` was observed. Those are useful guardrails, but name/value matching is not complete taint tracking.

## Proposed design

### Taint representation and propagation

Add a taint label to the calc engine's `Value` representation, preferably as an optional compact bit/label field with a default of untainted. Keep labels separate from the user-visible value and from formatting/style metadata. Initially use one label, `secret`, with room for a small label set later. A secret field read returns the same value plus the label; a read is secret when its source field is classified secret by the existing naming rule or an explicit schema/privilege policy. Keep existing API serialization and `toStored` behavior from silently dropping security metadata: serialization boundaries must either preserve the label or explicitly consult it before converting to a plain value.

All value-producing operations must join labels from their inputs (`OR` for one-bit taint): operators, casts/coercions, text functions (`Upper`, `Middle`, concatenation, Base64), JSON/XML helpers, custom functions, `Let`, `Evaluate`, and error/return paths. A value derived from a secret remains secret even if the transformation produces a number, boolean, shortened string, hash, or empty-looking result. Literal constants stay untainted. A control-flow dependency can leak too (`If(secret; "yes"; "no")`), so the result must include the taint of the condition as well as the selected branch. Where a function or plugin cannot report provenance, conservatively taint its result if any argument is tainted; unknown calls that can read data should be treated as tainted when their inputs or accessible sources include a secret.

Field reads, relationships, `GetField`, `ExecuteSQL`, and summary functions are sources and must return labelled values. `Pass.values` already caches `Value`, so it can retain labels, but cache keys must continue to distinguish privilege/account context. Script local variables and session `$$` variables must store the labelled `Value`, not a stringified copy; read/write APIs and script result/trace/action structures must keep labels until the final sink. Resetting or replacing a variable replaces its label along with the value.

### Persisted values

Taint must survive commits. The recommended first implementation is a per-value provenance bit alongside stored values, persisted in a sidecar table keyed by file, table, record ID, field ID, and repetition; global values and session variables get corresponding metadata. Update it atomically with the value. A write copies the source label: `Set Field`, auto-enter, lookup, import/mapping, replace, and script write steps must not clear taint. Stored calculations inherit the joined source labels at recompute time. Unstored calculations are labelled on each evaluation. Summary taint is the join over its contributing rows and must be invalidated/recomputed with the same lifecycle as summary values.

This is conservative and potentially sticky: overwriting a secret-derived field with a public literal clears taint, but ordinary transformations cannot. FileMaker source imports and existing databases need a bootstrap policy. Safe initial choices are to treat existing values in secret-named fields as tainted on read and lazily record provenance when values are rewritten, or to mark all stored calculations/auto-enter outputs whose dependency graph may include a secret as tainted until recomputed. The latter can over-taint significantly. Persisting the origin set (rather than one bit) would enable better clearing and explanation but costs more space and makes dependency updates harder. The one-bit design should not claim precise declassification.

`Set Field` from a secret source to a public-named destination must remain tainted after commit. Reopening a file, a new session, a cache rebuild, or an import cannot clear that mark. An administrative data rewrite or an explicit trusted declassification operation is required to clear it. Such declassification should not be exposed to an AI caller.

### SQL, summaries, and sinks

The hard engineering choice is SQLite. `sql_query` executes against SQL tables and can calculate expressions without passing through calc `Value`s. Two viable implementations are: (1) add provenance columns/sidecar lookups to the SQL execution layer and evaluate scalar/aggregate expressions with taint-aware functions, including tainted `*` expansion; or (2) for the first phase, reject or withhold an AI SQL result if its read set includes a tainted field or an expression/virtual source whose provenance cannot be proven. The latter has more false positives but a smaller bypass surface. `ExecuteSQL` inside formulas must use the same policy and return labelled values or refuse a secret-dependent result.

Summary reducers join taint from every input row and all group keys. Where a tainted measure contributes, mark the output tainted; where only a predicate/group key is tainted, mark affected membership, labels, and counts too. For whole-table shared caches, taint is part of the cached result and invalidation key. Do not expose tainted values through a partial/stale summary while a clean refresh runs.

Make the final AI boundary a mandatory sink check, not a collection of ad hoc redactors. At minimum it must check record/portal fields, `sql_query` rows, summary/dashboard/chart payloads, script return values, variables included in results, traces, errors, access-denial detail, outbound/action descriptions, container previews/downloads, and exported file bytes. For a tainted output, return a stable placeholder or a clear withheld-result note; never stringify the underlying value first. Continue applying existing name-based redaction as a fallback for legacy records with no taint metadata. Non-AI surfaces preserve their existing behavior, subject to the account's normal privileges.

## Costs and compatibility

These are engineering estimates, not measurements; a benchmark is required before rollout. With a JavaScript boolean property, a `Value` gets roughly 8 bytes of payload per instance before object alignment, and may increase the object shape/size by roughly 8–16 bytes. A packed flags byte or shared tainted/untainted representation may reduce that. At one million simultaneously live `Value` objects, the direct cost is roughly 8–16 MB; actual heap growth could be higher because of object alignment and map retention. Most values are short-lived, but `Pass.values`, SQL rows, summary buffers, and script variables retain values across work. A single bitwise join per operator is negligible in isolation; propagation through every built-in function and SQL result materialization is on hot paths, so target under 3% CPU and under 5% heap in representative calculation/script workloads. These targets are estimates, not established results.

Persisted sidecar provenance adds one bit logically but at least a row/key and SQLite index overhead physically. A dense bitmap keyed by stable field/record slots could approach 1 bit per value (about 125 KB per million values), while a sparse table could cost tens of bytes per tainted value and much more with indexes. Migration, backup/restore, compaction, rollback, transaction atomicity, sync/versioning, and writes from paths outside scripts must all be addressed. The real cost depends on the secret prevalence and whether the sidecar is sparse or dense.

Compatibility risks include changing the public/internal `Value` shape; external/custom functions that create values and drop labels; calculations whose control flow now marks a result secret; old files and stored calculations without provenance; SQL expressions the engine cannot analyze; increased withholding of safe data; stale caches and summary warmers; script results that are withheld where they previously returned transformed data; exported files and container download behavior; and persisted metadata across import, clone, backup, restore, and file upgrades. Existing calculation semantics and serialized field values must remain byte-for-byte unchanged outside AI sinks.

## Phased plan and tests

1. **Inventory and benchmark.** Map every AI response sink and every write/materialization path. Add representative baseline measurements for calc-heavy, script-heavy, SQL, summary, and record-read workloads. Tests: source-path inventory assertions and baseline benchmark fixtures; no behavior change.
2. **In-memory calc taint.** Add labels to `Value`; propagate through operators, all built-ins/custom-function boundaries, branches, coercions, fields, relationships, globals, `ExecuteSQL`, and unstored calculations. Tests: secret unchanged, transformed (`Upper`, `Middle`, Base64), arithmetic/boolean/control-flow, aliases, related values, custom functions, and a clean-input control.
3. **Script and AI sinks.** Preserve labels in `$`/`$$`, script results and actions; centralize final AI serialization/redaction. Tests: secret crosses steps and runs via `$$`; trace/error/exit/action paths; web assistant/MCP record, SQL, summary, dashboard, container, and export outputs; assert the secret bytes never occur in any returned payload.
4. **Persistence and summaries.** Persist taint atomically for ordinary fields, globals, stored calculations, auto-enter/Set Field copies, and containers; join and invalidate summary/cache taint correctly. Tests: commit/reopen/new session, copy into innocently named fields, recomputation, overwrite with public literal, rollback, import, backup/restore, stale summary refresh, and cross-account privilege contexts.
5. **SQL and rollout.** Implement SQL taint propagation or the conservative read-set refusal policy, then enable per file behind a feature flag and observe false-positive/latency rates. Tests: aliases, expressions, `*`, joins, aggregates, subqueries, union, virtual tables, `ExecuteSQL`, and attempts to recover bytes with casts/substring/encoding. Roll out gradually only after performance targets and sink coverage hold.

## Cheaper alternatives

* **AI-visible privilege flag:** refuse AI tools access to any layout/table containing a secret-named field unless that account's privilege set marks the field AI-visible. This is simple and robust against transforms, but can make an entire layout/table unavailable and needs a clear policy schema plus review UX. It is the strongest low-cost interim boundary.
* **Conservative refusal by read set:** withhold an entire SQL/script/summary response when the source table or script may read a secret field. This is close to current script behavior and easy to extend, but causes false positives and needs complete read-set discovery to avoid gaps.
* **Secret-field quarantine:** exclude secret-named fields from AI tools at the query planner and deny calculations/scripts that depend on them. This is better than output matching but dynamic references and persisted copies remain difficult without dependency tracking.
* **Keep name/value matching and improve heuristics:** low implementation cost, but transformed values, globals, copies, numeric aggregates, and unknown expressions continue to evade it. It should remain a fallback, not be described as complete protection.

## Recommendation

For an interim improvement, add an explicit AI-visible privilege policy and make AI tools refuse layouts/tables that include secret fields by default; pair it with conservative refusal for SQL or scripts whose read set is uncertain. For a full r17 taint effort, prototype labels first in calc `Value` and prove complete propagation through scripts and AI sinks, then design persisted sidecar provenance and SQL policy before claiming protection. Do not ship a runtime-only bit as complete taint tracking: stored calculations, `Set Field` copies, containers, and SQL can outlive or bypass it. Keep account field privileges as the actual access control, and present taint as defense in depth with documented false-positive and declassification limits.
