# Native field types (N2)

These five types are available only in native files. Compat definitions and stored values keep their existing behavior. `NATIVE_FIELD_TYPES` in `packages/store/src/design.ts` identifies fields that cannot be exported to a compat file.

| Type | Stored form | Write and read behavior |
| --- | --- | --- |
| boolean | `BOOLEAN`, integer 0 or 1 | Accepts `true`, `false`, `1`, `0` (words case insensitive). Data API and OData read as JSON booleans. |
| integer | `BIGINT`, integer | Accepts whole numbers within JavaScript's safe integer range (±9,007,199,254,740,991). Data API and OData read as JSON numbers. |
| decimal | `DECIMAL_TEXT`, canonical text | Accepts signed plain decimal strings with at most 1000 integer digits and 30 fractional digits, including `.5` and `5.`. Leading integer zeros and trailing fractional zeros are removed; negative zero becomes `0`. Data API and OData read as strings. A JSON number is accepted only if it is a safe integer or its shortest round-trip representation has at most 15 significant digits; send a string for longer decimals. |
| json | `JSON_TEXT`, canonical text | Accepts JSON text, or a JSON object or array through Data API and OData. Object keys are sorted recursively, insignificant whitespace is removed, and original number tokens are retained. Duplicate decoded object keys and values over 1 MiB in UTF-8 are refused. Data API sends JSON values with original number tokens; a JavaScript client can still round them when it parses the response. OData and SQL read canonical JSON text. |
| uuid | `UUID_TEXT`, lowercase text | Accepts 8-4-4-4-12 hexadecimal UUIDs, case insensitive. Reads as lowercase strings. |

An empty write clears any of the five fields. Empty values appear as `null` in Data API and OData JSON, and as empty values in the store's record API. Invalid nonempty writes receive validation error code 500 and HTTP 400 from Data API and OData. JSON size and depth errors name the violated limit. Data API layout metadata reports each native type by its own name; XML export maps boolean, integer and decimal to `NUMBER`, and JSON and UUID to `TEXT`.

Stored decimal text retains exact digits. Find and native sorts use `fm_decimal_key` for exact decimal ordering. Equality relationships use indexed canonical text for native decimal fields and normalized parameters for native UUID fields. Decimal range relationships use an expression index on `fm_decimal_key`. UUID relationship comparisons ignore case. JSON Find matches the complete canonical JSON value; `*` matches any nonempty JSON value; range operators are refused. Find and OData filters refuse exponent literals with an error. OData accepts unquoted UUID literals only for native UUID fields and compares them case insensitively. Invalid decimal filter literals match no records. OData `$apply` uses exact decimal ordering for min and max, returning the stored text; sum and average use SQLite numeric arithmetic.

Calculation fields treat decimals as JavaScript numbers for comparisons, `If`, and arithmetic. This conversion can lose precision for values beyond the JavaScript number range or about 15 significant decimal digits. Direct store reads retain the exact canonical text; `GetAsText` in a calculation sees the converted number. JSON and UUID calculations see text.

ExecuteSQL, HTTP SQL and pgwire use a read-only SQL view that casts decimal columns to SQLite `REAL`. Their `WHERE`, `ORDER BY`, `SUM`, `AVG`, `MIN` and `MAX` therefore operate numerically. This SQL projection uses binary floating point and can lose precision; use Data API, OData or direct store reads when exact stored decimal digits matter. The `fm_decimal_key` function is also registered on the read-only SQL connection; explicit exact comparisons can address the stored text through `main."Table"`. PostgreSQL reports the SQL projection as `numeric`.

For native files, OData `IEEE754Compatible=true` in `Accept` or `$format` is reflected in the JSON response content type. Decimal values are strings either way, preserving digits on the wire; with IEEE754 compatibility, `Edm.Int64` values are strings too. Native OData schema creation maps `NUMERIC` and `DECIMAL` to `Edm.Decimal`, `INT`, `INTEGER` and `BIGINT` to `Edm.Int64`, boolean to `Edm.Boolean`, UUID to `Edm.Guid`, and JSON to `Edm.String`. Compat schema creation and response behavior are unchanged: the previous FileMaker number mapping remains, duplicate request keys retain their last value, unquoted GUID filters remain invalid, and IEEE754 compatibility is not advertised.
