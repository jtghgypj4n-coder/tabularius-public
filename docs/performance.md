# Performance

## Corpus scan scaling probe (2026-10-16)

The r9-34 `scripts/bench.ts` generator creates native SQLite stores, not
`.fmp12` files. A small generated-store probe used its design-then-direct-SQL
pattern, varied table, field, record, layout and calculation-chain counts, and
removed both temporary stores after timing. Node 22.22.2 on this Mac; one run,
so these figures are observations rather than stable limits.

| Tables | Fields/table | Records/table | Layouts/table | Calc depth | Design build | Record inserts | 20,000 field-name lookups |
| ---: | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| 4 | 12 | 200 | 2 | 4 | 139 ms | 800 in 17 ms (47k/s) | 2.88 ms |
| 8 | 24 | 400 | 4 | 8 | 107 ms | 3,200 in 26 ms (123k/s) | 2.87 ms |

The reader and converter review found repeated linear field, table, occurrence,
layout and relationship lookups, and a scan formula-shape loop over every
previously seen plug-in name. Those paths now use indexed maps or one pass over
each formula; repeating-field membership during conversion uses a set. Shape
extraction reads at most the report's 240-character cap per call. Resumed
conversion also indexes completed table names once, rather than checking all
previous tables for each next table. The generated
SQLite stores cannot measure `.fmp12` block walks or conversion SQL directly;
measuring those stages against generated `.fmp12` files remains follow-up work.

How long common work takes on a large file: opening it, finding, sorting,
summary fields, ExecuteSQL, import, export, backup and restore. Use these numbers as a baseline, so a change
that makes one of them slower is noticed. They aren't a promise for any
particular solution.

## Running the benchmark

```sh
npm run bench                          # 200,000 invoices, 5 runs of each operation
npm run bench -- --records 1000000     # a bigger file
npm run bench -- --markdown            # the table below, ready to paste here
npm run bench -- --json                # every timing, for comparing runs
```

Options: `--records N` (invoices, default 200,000), `--customers N` (default
5,000), `--runs N` (default 5), `--import N` (rows to import, default
100,000), and `--keep`, which leaves the database in
its temporary folder and prints where it is.

The benchmark isn't part of `npm test` or CI, because timings depend on the
machine. Run it before and after a change that might affect speed, on the
same machine, and compare.

## What it measures

The file is **synthetic**, generated by `scripts/bench.ts` from a fixed seed,
so every run measures the same data. No `.fmp12` and no real or customer
file is used. Its design is made through the store and its records are
written straight into SQLite. It has two tables:

- **Customers:** an id, a name and a city.
- **Invoices:** customer id and name, region, date, amount, status and a
  notes field of a few words, and Tax, an unstored calculation (Amount × 0.2).
  It is related to Customers.
- **Imported:** an empty table of an id, a name, a city and an amount, which
  the import fills.

It has two layouts on Invoices:

- **Invoices** has three summary fields: Total, Average and Count of Amount.
- **Invoice List** has the same fields without the summaries.

Each operation reads one page of 50 records, as the web client and most Data
API calls do, and only the layout's fields (`layoutOnly`). It runs in one
process against the store, with no HTTP in between.

| Area | What is timed |
| --- | --- |
| Open | A fresh `Store` on the file, through to its first page of records, as a server does when it hosts a file. |
| Find | Word, name, number range, date range, two fields, two requests with an omit, and a range on an unstored calculation (worked out for every record, as it has no stored value). The first text find builds the word index (see [ARCHITECTURE.md](ARCHITECTURE.md#several-users)). |
| Sort | All records by a text field, a number field, two fields and an unstored calculation, and a found set by a text field. |
| Summary fields | Total, average and count over all records and over a found set. |
| ExecuteSQL | SUM with WHERE, COUNT with GROUP BY, a JOIN to Customers, and ORDER BY with FETCH FIRST. |
| Import | Planning and importing `--import` rows of four text fields into the empty Imported table, as an import file with a header row is read. Done once. |
| Export | Every invoice's stored fields as comma-separated text, in pages of 500, built whole in memory as the web client's export does. Done once. |
| Backup, Restore | Copying the hosted folder into a new backup set, and the set back into an empty folder. Done once each. |

Tabularius keeps summary and ExecuteSQL results while the data is unchanged, so
these rows are timed two ways:

- **"after a change"** edits one invoice before each run, so the work is done again.
- **"unchanged"** repeats it with no edit in between.

**First** is the first run. **Median** and **min** are over the runs after it.

## What the baseline shows

- **Opening is cheap.** A hosted file is a SQLite database, so opening a
  200,000-record file and reading its first page takes about 10 ms.
- **The first text find in a table pays for the word index.** It took about
  1 s here. Later finds on text take about 50 ms or less.
- **Sorting by text is about fifteen times slower than sorting by a number.**
  It took 0.5 s for 200,000 records, against 35 ms by Amount. This is the
  sort to watch.
- **Summary fields over all records take about 1.1 s after each change.**
  While nothing changes, they come back in under 1 ms.
- **Summary fields over a found set are worked out on every read.** They took
  about 0.3 s for 40,000 records, even with nothing changed. This is the most
  obvious thing to improve.
- **ExecuteSQL is fast.** Its queries run in SQLite and are kept while the
  data is unchanged, so the slowest one here was a JOIN with GROUP BY, at
  about 180 ms.

### A layout pays for every summary field it names

A layout's reads work out every field it uses. That includes:

- the fields placed on it
- its Table View columns
- any field named in its text, such as a label that says "Total Amount"

An early version of this benchmark left the generated form's labels and
Table View columns in place on Invoice List. That made each 50-record read
total all 200,000 amounts, about 1.1 s. When a list layout is slow, check
whether it names a summary field it doesn't show.

## The guard against slowdowns

The benchmark above is run by hand. Two tests run on real files, the two Beezwax demo files in `fixtures/`, with limits set at about ten times what a slow machine takes, so a busy runner passes and a real slowdown fails:

- `packages/server/test/performance-guard.test.ts` (part of `npm test` and CI) times converting and hosting both files, hosting them again, and, for every layout, the first page of 50 records, a sorted page, a found set and a record with its portal rows. It fails with the operation, its median and its limit.
- `packages/web/e2e/first-paint.e2e.ts` (run with `npm run test:e2e`) times pressing Open to the first layout drawn in the web client.

Both print their numbers. Set `TABULARIUS_PERF_OUT` to a file name and the server test writes them there as JSON (the web test writes `<name>-web.json` beside it), so a run's numbers can be kept and compared; without it the server test writes `tabularius-perf.json` in the temp folder.

## Five-million-record scale probe

Run `node --max-old-space-size=2048 scripts/scale-5m.ts` separately from the
test suite. Its JSON output includes the machine, native file and CSV sizes,
each operation's elapsed milliseconds, sampled `process.memoryUsage()` and
peak resident memory. `--records 200000` runs the same path with fewer rows.
The script requires 20 GiB free on the temporary volume and a one-minute load
average below 20 before it makes anything; it removes its temporary folder
afterward, including on failure. It binds HTTP and pgwire only to `127.0.0.1`.

The input is generated in code and bulk-loaded into a native SQLite store.
The import timing includes all 5,000,000 inserts, index creation and `ANALYZE`.
There is no synthetic `.fmp12` converter in this probe, so it does **not**
measure Claris file conversion; conversion performance and Claris behavior at
this size are unknown. The other timings cover an indexed Id find, a verified
unindexed Notes scan, sort and list first pages, a whole-file summary and
sub-summary, Data API `_find` with offset, OData `$top`/`$skip`, pgwire
`SELECT ... LIMIT`, HTTP CSV export and a verified backup. The index and scan
labels describe the actual SQLite query plan; the unindexed scan uses SQL
`LIKE` because a FileMaker text find may build its own word index.

The 5M results are pending: on 2026-10-17 the available space was 24 GiB but
the one-minute load average remained above 20 (32–40 during checks). The
guard therefore prevented the measurement. The generated 200k regression
test exported all rows in 3.7 s on Apple M5 Max (18 logical CPUs, 128 GiB
memory), macOS 26.4, Node v22.22.2, but that is a test result, not a 5M
estimate. Do not extrapolate a 5M result from it.

## Drawing big layouts in the web client

`packages/web/e2e/render-budgets.e2e.ts` (browser tests, `npm run test:e2e`) builds one synthetic file (10,000 Items with 42 fields, an Owner with 500 related Lines) and times the web client drawing six layouts that stress it. Each is timed inside the page, from the layout menu changing to the content on screen and a frame drawn (**paint**) and the main thread free again (**free**), with how long the page was blocked in long tasks (over 50 ms) and how many elements the page holds afterwards.

| Layout | Paint (ms) | Free (ms) | Blocked (ms) | Elements | Budget: paint / elements |
| --- | ---: | ---: | ---: | ---: | --- |
| 1,500 objects (500 fields, 1,000 texts) | 162 | 163 | 84 | 3,185 | 600 ms / 9,600 |
| List view of 10,000 records | 56 | 57 | 0 | 734 | 500 ms / 2,200 |
| Table view, 40 columns, 10,000 records | 201 | 202 | 157 | 3,591 | 700 ms / 10,800 |
| Portal of 500 related records (scrolling) | 199 | 199 | 73 | 3,652 | 500 ms / 11,000 |
| 30 tab panels, 30 popover buttons | 68 | 68 | 0 | 1,522 | 500 ms / 4,600 |
| Column chart of the 10,000 records found | 429 | 430 | 210 | 10,171 | 1,200 ms / 30,500 |

Measured on 2026-10-17, at commit `7e6256f4` plus this change, on a cloud container: Node v22.22.0, Intel Xeon @ 2.10 GHz × 4, 15 GB memory, linux, Chromium from Playwright, headless, no throttling. Server and browser share the machine and the data is local, so these are drawing times, not network times.

The budgets are three times these numbers, or a floor of 500 ms for times (a few milliseconds measured would fail any slow runner at three times), and the test fails with the layout, the number and the budget. The element budgets do not depend on the machine: the list's is what keeps a list of 10,000 records drawing only the rows in view (about 700 elements, not 100,000).

What the numbers show:

- **Lists and table views draw only the rows in view** (the page keeps about 50 and a spacer), so 10,000 records cost no more than 50.
- **Hidden tab panels are built with their tab control**: 30 panels of 20 objects cost 68 ms, so they are not built later.
- **Popovers are built when opened**, so 30 of them add nothing to the first draw.
- **A portal draws every row it has**, 500 rows of three fields in about 200 ms. It is not windowed; the server sends a record's portal as 50 rows, and the web client now fetches the rest (up to 2,000) as soon as the layout is drawn and adds them under the first 50 (before this, a portal showed 50 rows however many related records there were). Past 2,000 rows a portal needs windowing, which isn't done.
- **The chart is the largest page**: a found-set column chart of 10,000 records builds a shape for each record (10,171 elements). Drawing it differently would change how it looks, so it is measured and budgeted, not changed.

Set `TABULARIUS_PERF_OUT` and it writes `<name>-render.json` beside the other web numbers.

## Launch-day overload capacity

On 2026-10-17, a three-second synthetic HTTP load test ran on macOS 25.4, Apple M5 Max (18 reported CPUs), 128 GiB RAM, Node 22.22.2. With one worker and 5,000 generated records, 64 concurrent mixed-workload sessions gave find p95 of 311 ms at 850 completed requests/s; 96 sessions gave find p95 of 805 ms at 629 completed requests/s and 20 HTTP 503s. Find p95 remained below one second through 96 tested sessions, including a 30,000-record file, because the gate shed work first. The lower completed rate at 96 sessions reflects closed-loop clients waiting and requests shed under overload.

With 16 signed-in sessions and a fixed offered find rate, 800 finds/s had p95 of 28.6 ms and no refusals; 1,000 finds/s had p95 of 105 ms but 60 refusals; 1,200 finds/s crossed one second at p95 of 2,019 ms with 179 refusals. Server RSS rose from about 190 MiB before traffic to 365 MiB at 800 finds/s and 413 MiB at 1,200 finds/s. These short samples show transient growth, not a steady-state memory limit.

The recommended starting point on that machine for this workload is `serve --workers 2` with the default per-worker gate: `TABULARIUS_REQUEST_LIMIT=32`, `TABULARIUS_REQUEST_QUEUE=64`, and a 750 ms queue wait. Two workers served 96 mixed-workload sessions at find p95 of 402 ms with no refusals. The gate reserves two slots for sign-in and assets, favors them over finds and exports, and sheds with HTTP 503 plus `Retry-After: 1`. Monitor `tabularius_request_gate_queue_depth` and `tabularius_request_gate_shed_total`. See [the full overload audit](audits/r20-11-overload-capacity.md) for methods and limits.
